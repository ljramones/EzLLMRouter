# Duranki / Mach-Platform static LLM reconnaissance

**Disposition: COMPLETE_WITH_EXPLICIT_GAPS.** Inspected 16 October 2026. This is source evidence for a future standalone client contract, not runtime conformance, implementation acceptance, a gateway proof, or Vega integration approval.

## 1. Executive findings and decisions informed

1. **There is no single LLM dispatch seam.** The source census found 98 `messages.create`/`messages.stream` call expressions in 79 application/package files, grouped into 26 families when direct HTTP and realtime voice are included. The counts measure source expressions, not traffic. Vega chat, Proto chat, My Assistant, editorial agents, detectors, coding agents, xAI Responses, and realtime voice use distinct paths. The machine-readable inventory names every SDK call expression found in `apps/`, `lib/`, and `packages/` and the representative direct transports. [SOURCE_CONFIRMED; inventory plus `lib/vega-chat.js:7760-7794`, `lib/proto/chat-body.js:180-212`, `packages/@agents/my-assistant/body/index.js:973-1007`, `lib/vega-realtime.js:2090-2111`]
2. **The client must preserve structured messages and tool call identity.** Both legacy Vega chat and Proto chat put assistant `tool_use` blocks back into the conversation and follow with user `tool_result` blocks keyed by `tool_use_id`. Flattening to text would change execution. The application owns tool effects. [`lib/vega-chat.js:7794-7827`; `lib/proto/chat-body.js:191-212`]
3. **Request preparation is provider-dependent and can change semantics.** The Vega compatibility adapter removes `cache_control`, normalizes tool schemas, and changes forced tool choice to `auto` on xAI/Moonshot; the Anthropic path returns the input unchanged. A canonical work hash and candidate adapter version must be checked after this preparation, per baseline §5.3–5.4. [`lib/vega-chat.js:195-239`; baseline §5.3–5.4]
4. **Model identity and prompt content are mutable at request time.** Chat model config is refreshed from the database with env/default fallback; prompt blocks are cache-backed and editable, with a version in the schema. Request-time content/version must be captured or materialized before canonical-work binding. [`lib/vega-chat.js:123-158`; `lib/vega-prompts.js:37-43,59-93,109-126`; baseline §5.3]
5. **Current success/usage semantics are uneven.** The usage wrapper captures only calls through its instrumented client and an active AsyncLocalStorage context; its aggregate labels a multi-model run by the first model. A direct xAI wrapper substitutes zero counters when provider usage is absent. These are compatibility observations, not acceptable Duranki accounting rules. [`lib/llm-client.js:47-103,106-130`; `lib/vega-coding/xai-provider.js:75-82`; baseline §10.2]
6. **Streaming and realtime voice need explicit onboarding decisions.** Chat SSE and Proto chat consume deltas before final message assembly; voice uses a stateful WebSocket protocol. The baseline says internal agent steps use `streaming: false`; it does not prove every current streaming path is eligible for the first release. [`lib/vega-chat/dispatch.js:194-235`; `lib/proto/chat-body.js:180-235`; `lib/vega-realtime.js:4-21`; baseline §5.3]

## 4. Prompt, request, response, and state findings

**Prompt and source construction.** Chat can read `prompt_blocks` cache; the DB interface exposes key/content/version/updated actor, and a write updates DB plus cache (`lib/vega-prompts.js:37-43,59-93,109-126`). Legacy chat adds runtime model awareness to a system block and appends a copy-on-write note to the last outgoing user message (`lib/vega-chat.js:256-273,307-317`). The latter is a post-history transformation and must be included in canonical work if it reaches the provider. Mobile lite uses a six-turn history and no tools (`lib/vega-chat-stream.js:124-153`); the dispatcher uses up to 20 recent turns (`lib/vega-chat/dispatch.js:162-172`). Decomposer builds a default-claimant directive in the outgoing user message (`lib/vega-decomposer.js:238-257`). No universal block lineage or taint representation was established in the inspected request builders; absence is **NOT_FOUND_IN_INSPECTED_SCOPE**, not a universal absence.

**Provider and request contract.** The chat wrapper accepts Anthropic message shape (`system`, `messages`, `tools`, `tool_choice`, `max_tokens`, model). Selection can change per request; xAI/Moonshot compatibility adaptation removes cache hints and alters forced tool choice (`lib/vega-chat.js:123-239`). The root declares Node `>=24 <25`, npm workspaces and CommonJS entry (`package.json:1-13`); the lockfile pins `@anthropic-ai/sdk` 0.112.5 (`package-lock.json:79-82`). `packages/@agents/my-assistant/package.json:17` declares a different semver range. No SDK default behavior was proven by static app source. Multimodal image/PDF, audio transcription, realtime audio, direct Responses web search and chat completions are separate shapes; including them in Duranki Phase 1a needs an explicit capability decision.

**Response and partial output.** Nonstream chat reads `resp.content` tool blocks, `resp.stop_reason`, `resp.model`, `resp.usage`; tool results are looped back by ID, while a tool summary and input/result can be persisted (`lib/vega-chat.js:7791-7863`). Streamed dispatcher emits text before `finalMessage()`; if final assembly fails, it can continue with accumulated text (`lib/vega-chat/dispatch.js:194-235`). That is partial delivery and requires a separate outcome from accepted work. Decomposer salvages bare JSON when a forced tool call is absent; if neither succeeds it tries another candidate (`lib/vega-decomposer.js:268-299`). Outliner filters invalid item kinds and may synthesize required stubs (`lib/vega-agents/composers/composer-outliner.js:286-324`). These are application interpretations; Duranki should preserve raw and normalized response detail and let the orchestrator decide substantive acceptance.

**Retry, cancellation and outcome.** The chat client configures timeout and retries for xAI/Moonshot, and the default client must be read separately (`lib/vega-chat.js:169-192`). Vega nonstream performs first-turn provider failover; the decomposer performs up to three candidate attempts including contract failures (`lib/vega-chat.js:7760-7789`; `lib/vega-decomposer.js:259-299`). Coding preflight makes one semantic corrective call (`lib/vega-coding/claude-sdk-provider.js:548-585`). Composer state can be mirrored in Postgres and recovered as interrupted (`lib/vega-composer-dispatch.js:301-326,337-355`). A baseline-style `step_id`/revision, `execution_generation`, durable dispatch intent, unknown-outcome exposure, and compare-and-swap winner were **NOT_FOUND_IN_INSPECTED_SCOPE** of these paths; they remain Duranki/orchestrator contract additions under baseline §8.2–8.5. Cancellation propagation across all layers is **UNRESOLVED**.

**Identity, handling and accounting.** `dispatch()` accepts an optional `principal` string for telemetry (`lib/vega-chat/dispatch.js:4-17,67-76,358-365`); this field alone is not authenticated identity. Tool effects receive `by` and `sessionId` (`lib/vega-chat/dispatch.js:239-245`; `lib/vega-chat.js:7802-7806`). `llm-client` only records usage for instrumented create calls inside `withUsage`, and its aggregate loses per-model attribution (`lib/llm-client.js:47-130`). Other paths directly expose `resp.usage`, while `xai-provider` substitutes zeros for missing usage (`lib/vega-coding/xai-provider.js:75-82`). Baseline §5.1, §9, §10 and §13 require authenticated principal/owner, purpose, source restrictions, lineage, versioned usage semantics, and retention at persistence boundaries. These facts cannot be manufactured by an untrusted network SDK. Application and trusted service context must supply them, and the server must enforce them. No source-call count proves spend, savings, task correctness, or live frequency.

## 5. Recommended minimum standalone client surface

1. **Transport-neutral canonical request builder** for ordered system/user/assistant blocks; text and structured content; tool definitions and tool choice; model alias/pin; settings including output limit, timeout/deadline and cancellation; stable references with content version or materialized hash. This is an SDK recommendation derived from the observed shapes and baseline §5.3. Preserve provider-specific extensions only through explicit capability profiles and adapter versions.
2. **Trusted call context** containing authenticated principal from the service session, task owner, service/charging owner for background work, purpose, task/subtask/session, `step_id` and revision, `execution_generation`, source labels/restrictions, and trace context. The SDK can serialize these; the server must validate them. Phase 1a may use the baseline's explicitly flagged migration metadata gaps, never weakened identity, purpose, destination, source or retention checks (§5.1, §9).
3. **Rich response envelope** with ordered content blocks, tool IDs and arguments, finish reason, refusal/truncation, provider request ID, served model, raw/normalized usage plus unknown status, and errors. For enabled streams, expose deltas and a final assembled result separately, with an explicit partial/uncertain state. Source basis: call families above; baseline §8 and §10.
4. **Network-only JS and Python SDKs in the Duranki repository.** JavaScript should work in declared Node 24 CommonJS consumption and ordinary async/AbortSignal conventions, with a separately importable distribution and no Python runtime on Vega hosts. Python has parallel contract behavior. This is a recommendation; the exact JS package module format and minimum Node support are owner decisions. No server runtime is chosen here.

## 6. Standalone harness implications and initial workflows

Start with synthetic: simple text generation with runtime model selection; two-turn tool cycle preserving `tool_use_id`; forced structured result plus text-JSON fallback and rejection; multi-step composition with draft acceptance owned by a simulated orchestrator; retrieval/document block with source restrictions; background service-principal call; provider timeout/unknown usage; partial stream/cancel; and direct raw-protocol negative requests that bypass SDK validation. The fixture catalogue states which checks come from source and which only from v1.1. Tests should assert independent server enforcement of authentication, purpose, destination permission, source labels, retention, candidate adapter binding, dispatch intent, and retry generation. They cannot establish Vega compatibility until a separately authorized integration milestone.
