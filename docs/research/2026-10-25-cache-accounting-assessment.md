# Duranki caching, accounting and cost control assessment

**25 October 2026 · Assessment only · No product-source, profile, dependency, credential or provider change**

## Verdict

**Do not add an external cache now.** The only supported live generation route is a bounded, tool-free OpenAI Responses text request. It already benefits from provider-native *implicit* prompt caching when that provider and model supply it, but Duranki neither chooses cache controls nor prices cached reads and writes. A cache hit or a reported write currently makes the calculated cost unknown and pauses the personal allowance. For a model with charged cache writes, the allowance's ordinary-input reservation is not a proven cold-request upper bound. The current schema can also call a missing write counter “not applicable” and settle at the ordinary-input rate. These are model-conditional financial correctness risks **before owner activation**, not evidence of an actual charge: the owner profile has no personal setup, selected model, published live rate or campaign, and no real provider generation has been run. [F1–F3]

The existing attempt ledger, exact-decimal arithmetic, unique-attempt reporting, separate unknown/estimated states, revisioned prices and restart-unknown handling are useful foundations. A provider-cache contract and a complete admitted price function are the smallest useful next work. The 22 October research paper's objective—cost per *accepted* task within a comparable class and quality/latency envelope—is sound as an evaluation design. Its production cache-hit magnitudes, cross-provider economics and proposed 22 changes are hypotheses for Duranki: the current route has no representative agent sessions or measured acceptance cohorts. [R1, A1]

**Immediate operational implication:** keep the owner campaign unconfigured and paid generation off while the supported model/rate contract is reviewed. This assessment does not select a provider, model, rate, currency or allowance. It does not recommend installing Redis, LMCache or a LiteLLM update.

## Separate cache decisions

1. **Provider-native prompt/prefix caching:** no new infrastructure. Preserve authorized provider-visible stable instructions and content, but keep task/authority labels and tool permissions intact. Admit only an explicit model-specific price contract that can bound cold writes, output and every enabled charge, then normalize disjoint counters and show the reported cache status. A local canonical work digest cannot substitute for a provider prefix match.
2. **Provider-managed cache objects:** not on the selected route. A future Gemini or similar create/reference/update/delete operation needs its own authenticated admission, signed handling/retention scope, trusted egress, object owner/expiry, storage-liability reservation beyond request completion and reconciliation. “Cache maintenance,” embeddings and prewarming are chargeable operations, never an unmetered bypass.
3. **Exact response/result reuse:** no current workload justifies it. If a later deterministic, read-only task class has repeated identical complete dependencies, start with a small in-process option *after* admission; require current authorization before serving, current source/version and handling/retention checks, a revocation rule, no-store exclusion, and no replay of tool actions. Mark `cache_hit` and original generation provenance; incur **zero new provider send**, no fabricated guard/send receipt, and keep internal serving cost, allocated original cost and hypothetical avoided spend separate. A shared store earns consideration only after replication, invalidation and hit-volume evidence.
4. **Semantic response caching:** off by default. Similar text can carry a different turn, permission, source version or requested action. A similarity hit is never permission to disclose content or perform a tool action. A future narrow, static, non-sensitive FAQ-like class would still need independent quality and revocation tests plus embedding costs and retention control. [L1]
5. **Self-hosted KV reuse/offload:** first measure the actual lab serving engine's native prefix caching. vLLM documents block hashing, optional per-request `cache_salt` and eviction [V1]; salt is a cache-reuse domain, not a replacement for authorization. LMCache supports CPU/remote tiers, but its own compatibility guide says engine, connector, ABI, model and backend must be validated as a matrix [M1]. Duranki has no observed lab engine/version or queue, prefill, cache occupancy, transfer and acceptance data here. An external tier would add network/security boundaries and potential transfer cost; it is premature.

For any future cache hit, the entry must be rechecked against current grants, source classifications, retention/no-store rules, model/prompt/tool versions and task identity *before disclosure*. An external service must not give the network-disabled LiteLLM worker provider credentials or a new egress path. Retrieval and checkpoint stores, duplicate-submission recovery and HTTP connection pools remain separate from response/prefix/KV caches.

## Operator view and bounded next tranche

An understandable one-attempt display should show: **total reported input**, ordinary input, cache read, each priced write lifetime, output including a reasoning subset, and other charge categories; label each value `reported`, `derived`, `not applicable` or `unknown`. Put calculated cost, exact price version and conditions beside the **reservation** and **remaining exposure**; keep invoice reconciliation separate. Summaries should show cost coverage and unknown attempts, not a misleading aggregate “savings” card. Use a compact cache status such as `reported read`, `reported write`, `no cache reported`, `unavailable` with a short note that billing status is not physical reuse. Control choices belong on the approved deployment/allowance, not another opaque free-form UI.

**Recommended single tranche, before any owner-activated paid route:** implement a versioned OpenAI Responses *cache-aware financial contract* for the already selected text path. Scope: registry price schema and model-family eligibility, bound calculation in Coordinator/personal campaign, exact guard-bound recipe controls only if supported by the frozen versions, usage normalization and retained allowlisted counters, campaign settlement/reconciliation, and operator usage labels. First make missing versus zero explicit; price reads, 30-minute writes and ordinary input without double counting; derive a cold/write upper bound from a validated applicable rate function and output limit; reject unsupported model/TTL/long-context or other billable conditions rather than estimating. Preserve existing synthetic price versions and historical revisions; migrate additively, do not reinterpret old rows or balances, and require an explicit audited reconciliation for any correction. No cache key or TTL is needed in this first tranche unless a chosen model/handling policy demands one, and the frozen SDK's 12-hour gap must remain disabled pending separate review.

Acceptance tests for that tranche: total/read/write disjointness; both write TTLs only when actually supported; missing and contradictory fields; reasoning as an output subset; cold cost above predicted hit; rate/model/version drift; ceiling/allowance exhaustion; unknown exposure across restart; actual selected worker → guard → controlled sender usage shape; historical versioned price correction without silent rewrite; no-store/current-access behavior. Keep the existing no-retry, one-send and worker-isolation checks. Before any **response** cache tranche, add exact dependency, current permission, revocation, source-change, no-store and tool-action rejection tests. Before any **KV** offload trial, record native-cache baseline and measure prefill/TTFT, transfer bytes/time, GPU/CPU occupancy, eviction, hit rate, tail latency, energy/capacity cost and acceptance under representative lab load.

After that correctness tranche, collect *opt-in, permitted* task-class cohorts with acceptance, latency, unique-attempt usage and price versions. Decide on result reuse or lab KV tiers only if they improve cost per accepted task without a quality or latency regression. No paid experiment is needed to make the above correctness decision. If a later provider cache conformance test truly requires payment, obtain a separate approval for an exact model/deployment, two synthetic prompts at/above that model's cache minimum, explicit request count, rate, maximum cold/write exposure and stop condition; no such selection is made here.
