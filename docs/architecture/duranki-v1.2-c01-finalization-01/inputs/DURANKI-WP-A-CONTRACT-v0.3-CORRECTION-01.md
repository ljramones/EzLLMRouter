## 1. Version, operations and result delivery (A01-01, A01-06)

**Proposal:** retain the proposed, not yet deployed wire identifier `0.2` for this review. Every JSON envelope has `contract_version:"0.2"`; every HTTP operation sends `Duranki-Contract-Version: 0.2`, including GET and DELETE-free cancellation. `/v1` is a route family, not a protocol minor-version promise. Header/body disagreement or any other version is `UNSUPPORTED_VERSION` (HTTP 426). There is no extension-field or minor-version tolerance in this candidate. Capability profile is separately `initial_1a@1`; it cannot bypass policy. JSON Schema Draft 2020-12 entrypoints are selected by the named local `$ref`; the bundle root itself is metadata, not an instance validator. `.invalid` in its stable `$id` is a nonresolving identifier, pinned to the local file; no network resolution.

### 1.1 Exact response-wait option and header

`submit(request, options?)` accepts omitted options, `{}`, or exactly `{wait_ms: N}`; `N` is an integer 0–30000 (booleans, fractions, strings, negative values and extra keys reject client-side as `SCHEMA_INVALID` before network I/O). Omission or `{}` selects 1000 ms and omits `Duranki-Wait-Ms`; an explicit value sends exactly one header whose value is canonical ASCII decimal `0` or a nonzero digit followed by digits, without sign, leading zero, whitespace or separator. Duplicate, malformed or out-of-range direct-HTTP headers receive 400 `ErrorResponse(SCHEMA_INVALID)` before admission. `SubmitOptions` and `WaitHeader` are data schemas for those two surfaces; the header's numeric 30000 ceiling is a semantic check after lexical validation.

The monotonic response-wait clock starts when the authenticated, parsed and admitted work record and caller-known handle exist, before planning/FDC; the response deadline is `min(admission_monotonic_time + wait_ms, task_deadline mapped to that monotonic clock at admission)`. An expired task deadline rejects admission as 422 `SEMANTIC_INVALID`. Zero permits immediate 202 after admission; 30000 is inclusive. Per-attempt timeout starts separately at transmission, is plan-bound and cannot be lengthened by this wait. A client disconnect may lose the reply but neither cancels nor proves stop; the SDK raises `TRANSPORT_OUTCOME_UNKNOWN` and never automatically retries. A completed candidate or known failure before the response deadline uses live 200/409/503/502; otherwise the service closes the wait with 202. Remote execution can continue, fail or become unknown after 202. `wait_option_cases` records absent, zero, boundary and invalid values; `TR-NOSTORE-WAIT-EXPIRY` records the no-store consequence.

### 1.2 Known terminal failure and no-store completion

A known remote error after transmission, or a response that cannot yield a usable candidate because its structure/parse failed, is stored as `submission_state:failed_after_transmit` with `terminal_attempt_id`, `terminal_failure` code `REMOTE_EXECUTION_FAILED` or `CANDIDATE_UNUSABLE`, and the named attempt in `dispatch_state:response_observed`. It has `candidate_access:unavailable_due_failure`, no `CandidateResult`, and an independent `PublicUsageView` that may be `not_recorded`, explicitly unknown, partial or later reconciled. The safe error contains correlation and retry guidance, never provider body or output. A known failure received during the open wait returns HTTP 502 `SubmitReply.failed` with matching handle/attempt/stage; Python/JS SDKs raise `DurankiError` exposing those fields for status recovery. After 202 or lost reply, authenticated `getStatus` returns HTTP 200 with the stored diagnostic; a status-service outage instead returns `ErrorResponse(INTERNAL_UNAVAILABLE)`. `outcome_unknown` remains only for remote uncertainty, with no terminal error. A known failure does not imply zero usage, nonbillable work or replay safety. `TR-KNOWN-REMOTE-FAIL`, `TR-LOST-REMOTE-FAIL` and `TR-CANDIDATE-UNUSABLE` exercise these alternatives as inert data.

No-store submissions are eligible for the same bounded wait, with a disclosed **live-only candidate** policy. The pending policy is derived from current effective retention at admission; any later stricter classification wins at status/read time. If the server itself closes that channel at wait expiry, it returns 202 `pending_result_policy:metadata_only_no_store`. When the attempt later produces a candidate, it records outcome and accounting metadata but discards prohibited content; status returns `completed`, `candidate_access:not_retained`, `result_unavailable_reason:wait_expired_no_store`, `delivery_state:none`, and no candidate. This is an explicit possibly paid, unavailable-result outcome; the SDK does not retry or claim asynchronous retrieval. Retained-content 202 uses `pollable_if_retained`, subject to read-time authorization/retention. Lost live replies remain separately ambiguous; they do not acquire a fabricated wait-expiry reason. This policy is proposed for A2 review and does not override an active no-content-store classification.

SDKs are independent network clients: future CommonJS root `DurankiClient` and Python `duranki_client.DurankiClient` expose equivalent method semantics and typed `DurankiError(code,http_status,retry_guidance,correlation_id)`. No server module import is part of either SDK; JavaScript import requires no local Python. The present `0.0.0` packages are inert (WP-FND Acceptance 01; `clients/js/package.json`, `clients/python/pyproject.toml`, `server/pyproject.toml`). Methods, exports, and wire contract remain proposals under DEC-08.

`SubmitReply` has exactly one of: `delivered` with a caller-known `WorkKey`, server handle, full candidate and public usage view; `pending` with both keys, `pending_result_policy` and no candidate; `rejected` with `Error`, caller-known work key and no handle/candidate; or `failed` with handle, attempt ID, `failure_stage` and stored safe `Error` after a known pre- or post-transmit failure. A server rejection may occur before it has a submission ID. Transport loss has **no reply** and does not prove non-dispatch. The caller queries by authenticated WorkKey; `not found` means no visible record at that moment, **not** proof of non-execution. In 1a the SDK never automatically resubmits after ambiguous transport loss, even with the same generation. The orchestrator decides whether/how to recover; a new generation requires its authorization. Durable cross-replica deduplication is a full-1b guarantee, not inferred from the lookup API (architecture §§8.2–8.5). `SubmitReply` in the vectors shows delivered, pending, rejected and stored-failure forms.

`CandidateResult` contains a `PublicUsageView` snapshot and `attempt_id`, `execution_generation`, `candidate_id`, actual served `configuration_ref` and resolved destination, ordered output blocks (text and tool calls), `finish_reason`, structural check result, and observed time. It is provider/gateway evidence, never a step verdict. A multi-round tool exchange is **multiple submitted generations or steps**: caller receives a tool-call candidate, executes the tool under its own authority, then submits a new work item with a labelled tool result and matching call ID. The SDK neither executes tools nor performs semantic retry (architecture §§8.1, 11.1; static recce `lib/vega-chat.js:7794-7827`).

Content is returned in the **live submit response**. Status carries `candidate_access`: `present`, `not_retained`, `expired`, `not_yet_available`, or `unavailable_due_failure`. `present` requires a candidate and authorization; every other access state prohibits a candidate; `unavailable_due_failure` requires a stored known terminal failure before or after transmit. Status may include content only if the effective retention class and consent permit a bounded result store. For a no-content-storage class, the service may keep metadata, usage, digest and attempt state but must not store output merely to support polling. A lost live response can leave the candidate inaccessible. If an ordinary response wait expires first, 202 explicitly says `metadata_only_no_store`; later known completion has `candidate_access:not_retained`, `result_unavailable_reason:wait_expired_no_store`, and no candidate. The orchestrator handles the unavailable result under its own authority. Expiry produces `expired` with metadata only. All read paths reauthorize principal/task scope and apply content policy at read time. The ledger never gains raw content by virtue of this API (architecture §13).

## 2. Source representation and exact work projection (A01-02)

### 2.1 Typed input and resolution

`SubmitRequest` has ordered messages; each message is a role-specific type. System messages contain `system_text` blocks and require a trusted prompt origin; user messages contain `content_text` or `reference_text`; assistant messages contain `assistant_text` or `tool_call`; tool messages contain `tool_result` with exactly one of `result_text` or parsed `result_value` object. Each block has unique `block_id` and verified lineage/sensitivity/restrictions. Labels asserted by a client are checked against the authenticated source authority and current classifier; they do not confer authority. Tool results must match exactly one prior call ID in the work context; duplicate/orphan IDs reject. All text, tool descriptions/schemas/arguments/results, derived fields and resolved reference content inherit the combined handling policy, not only the maximum sensitivity. `lineage_ids`, `restrictions` and `requested_features` are set-like: duplicates in a submitted array fail shape, and accepted arrays are sorted by UTF-16 code-unit order before projection; messages/blocks/tool definitions, prompt block IDs and reference placement are ordered. Tool-schema `required`/`enum` arrays retain their supplied order as an explicit part of this restricted work representation. A caller may not silently promote a user block to system authority (architecture §§5.1, 9; recce `lib/proto/chat-body.js:191-212`).

`InputPrompt` names `prompt_id`, immutable `prompt_version`, ordered `block_ids`, and `source_artifact_digest = SHA-256(JCS(immutable registry array of complete source system blocks before current classification))`. The trusted resolver verifies registry version, block identity, source-artifact digest, authenticated source authority and normalized equality of submitted blocks; a mismatch rejects before plan. After current classification and label normalization, `ResolvedPrompt.resolved_digest = SHA-256(JCS(ordered complete effective system blocks))`; this effective digest belongs to canonical work and can differ from the source-artifact digest. A resolver/classifier upgrade changes work binding and may require replan. No parallel unbound prompt text exists. A `reference_text` block occupies its exact message position. A versioned reference names controlled `reference_id`, immutable `content_version` and expected content digest; the trusted resolver fetches that exact version, verifies digest, labels/classifies text, and substitutes a resolved block retaining reference metadata **before** canonical binding. A materialized reference supplies text and digest, which the server verifies. Bare mutable URI/provider state rejects; failure to resolve/version/classify rejects. Reference namespace, prompt namespace and `configuration_ref` are approved registry IDs, not arbitrary provider strings. Actual endpoint/model/region come from the approved configuration resolver and are bound in the plan (architecture §§5.1, 5.3, 5.5, 13).

Tool arguments are parsed JSON **values**, not opaque `arguments_json` strings. The outer parser rejects duplicate keys/lone surrogates/nonfinite numbers throughout; arguments must be objects conforming to the named tool's approved input schema. The proposed tool-schema subset is local Draft 2020-12 object/array/string/integer/boolean, `properties`, `required`, `items`, `enum`, string length/pattern and integer min/max; no external or local `$ref`, `number`, `null`, combinators, defaults, remote formats, or unknown keywords. The subset is stored as a data object and validated semantically in addition to its outer shape. Limits: ≤64 KiB request JSON, ≤128 messages, ≤256 blocks, ≤32 tools, ≤32 KiB combined tool schema, ≤16 nesting levels, ≤1024 keys per object, ≤1 MiB resolved text per reference subject to a stricter active policy. Exceeding a limit rejects `LIMIT_EXCEEDED`; an unsupported tool schema or tool-choice translation rejects `CAPABILITY_UNSUPPORTED`. These bounds are **proposed**, not measured provider limits. Arbitrary text such as `"0.00"` is never numerically normalized.

### 2.2 `duranki-work-v0.2` projection

After authentication, reference/prompt resolution, source validation and explicit semantic defaulting, the **server** constructs exactly this object, with these keys and no others. The schema definition `CanonicalWork` matches it; vectors give complete synthetic instances. `trusted` comes from the trusted context, never client claims. `work` comes from validated request values and resolved blocks. `destination` comes from the approved configuration resolver.

```json
{"projection_version":"duranki-work-v0.2","trusted":{"principal_id":"…","charging_owner_id":"…","source_authority_id":"…","context_id":"…"},"work":{"task_id":"…","task_class":"…","step_class":"…","step_id":"…","step_revision":1,"execution_generation":"…","purpose":"execution","destination_config_id":"…","requested_features":["text"],"resolved_prompt":{"prompt_id":"…","prompt_version":"…","block_ids":["…"],"resolved_digest":"sha256:…"},"messages":["resolved typed messages"],"tool_definitions":[],"tool_choice":"none","generation_settings":{"max_output_tokens":32,"temperature_decimal":"0","total_timeout_ms":1000},"deadline":"2030-01-01T00:00:00Z"},"destination":{"configuration_ref":"…","service":"…","endpoint":"…","model":"…","model_version":"…","processing_region":"…"}}
```

Conditional `parent_call` and `construction_manifest_ref` appear in `work` **only when present and validated**; no nulls. `session_id` and `subtask_id` are in `work` when supplied; an explicit migration mode may omit only approved accounting/analytical metadata and marks the internal admission record non-compliant/ineligible for optimization. No semantic default is hidden: absent `tool_definitions` becomes `[]`, absent `tool_choice` becomes `none`, absent `references` are represented by no reference blocks, and required settings/deadline never default. Claimed principal/owner, request observation timestamp and trace context are excluded; the server either checks claimed IDs against trusted context or rejects mismatch. `source_labels` and all tool/restriction content are included within resolved blocks. Any current-classification upgrade must be applied before projection and may require replan; the snapshot is audit only. `work_digest = SHA-256(UTF8("duranki-work-v0.2\n") || UTF8(JCS(CanonicalWork)))`. `WorkKey` is the namespace-qualified tuple `(principal_id, task_id, step_id, step_revision, execution_generation)`, and equality for deduplication additionally requires equal `work_digest` (architecture §§5.3, 8.2).

**Restricted JCS input profile:** unique object keys, valid Unicode scalar strings, booleans, arrays, objects and safe integers `[-9007199254740991,9007199254740991]`; no JSON floats, `null`, NaN/infinity or negative zero. JCS sorts keys recursively by UTF-16 code units, preserves array order and string data, and emits UTF-8. Duranki normalizes **only** `generation_settings.temperature_decimal`, `financial_scope.max_attempt_charge_decimal` and accounting decimal fields before JCS: no exponent, leading plus or negative zero; strip fractional trailing zeroes and an empty point; minimum `0`. Monetary values have their separate 9-place scale rule (§5). UTC timestamps use exactly `YYYY-MM-DDTHH:MM:SSZ` without fractions in binding; offsets are parsed then converted to UTC before projection (the original lexical spelling is not identity). Invalid/ambiguous date or range rejects. Other strings are byte-preserved Unicode scalars, never trim/case/Unicode-normalized. An omitted optional field differs from explicit null; null rejects. Review 01 §7 separately verifies RFC 8785 and JSON Schema standards behavior; golden construction in vectors is a limited data calculation, not a production canonicalizer.

## 3. Trusted authorization envelope and final dispatch (A01-03)

`TrustedContext` is issued by the authenticated ingress/orchestrator identity service over a trusted internal channel. Its server-held `context_id` is a stable semantic authorization-context identifier scoped to `(issuer_id, principal_id, charging_owner_id, source_authority_id, task_id, authorized work scope)` for the lifetime of that authorized work; it survives credential refresh/reconnection but changes when owner/source/work authority changes. Fresh expiry, integrity and revocation checks still occur on every reliance. The issuer never reuses a context ID for a changed tuple. The server validates its issuer, integrity, expiry, revocation and scope; SDK headers/body claims are never substitutes. A service principal for background work has a named charging owner. A derived call carries `parent_call` and inherits the parent's combined restrictions plus its own. Office-origin, when present, is a separately signed internal attribute, never tracing baggage; forged/unsigned/wrong-session origin rejects at the first relying phase (architecture §§5.1, 9, 16 T-06). No real issuer or key is selected here.

`ExecutionPlan` is internal, signed by the optimization layer under a gateway-verifiable plan-signing key version. **Proposal:** signature envelope records `scheme:"Ed25519"`, `key_id`, `key_version`, signed-plan digest and opaque signature bytes. `signed_plan_digest = SHA-256(UTF8(JCS(ExecutionPlan without signature_envelope)))`; the signed message is `UTF8("duranki-plan-v0.2\n" || scheme || "\n" || key_id || "\n" || key_version || "\n" || signed_plan_digest)`. The synthetic string `SYMBOLIC_NOT_VALIDATED` in vectors is expressly **not** a valid signature. No actual key material is produced. Signed fields include work digest, principal/owner and scope, purpose/task/step class, fixed configuration/deployment, quality approval, adapter recipe/version, policy/recovery/registry/capability versions, current binding deadline, limits/decision and failure policy. Gateway verifies the signature under its held trust key before FDC; it never trusts an unsigned client plan.

`PreparedCandidate` carries the trusted work digest, approved config and adapter recipe, `expected_request_digest`, `observed_request_digest`, final byte length, and `preparation_match`. The **expected** bytes are independently regenerated from signed canonical work and the pinned deterministic adapter/callback recipe; the **observed** bytes are captured at the final gateway emission boundary after all adapters/callbacks and before transmission. FDC recomputes their digests itself and compares exact bytes/semantic binding, rather than accepting a `callbacks_complete` flag or self-reported digest. A recipe that cannot reproduce final semantics is unsupported. Gateway first checks plan signature, expiry, revocation and current policy/recovery/registry/capability versions; then obtains final prepared bytes and compares them to the signed work and pinned adapter recipe; then checks current classification/combined handling, destination permission, spend authorization/lease as applicable and deadline. FDC fails closed at the first failing stage, before intent. Any failure blocks intent and transmission. After passing FDC, durable `DispatchIntent` with attempt ID, plan/prepared digests and authorization time is the authorization point. Persistence failure blocks transmission. Revocation after intent but before transmit triggers recheck; after transmission, record and settle the attempt (architecture §5.4). WP-B must prove this with a pinned gateway and independent receiver; these records are merely shapes.

## 4. Attempt, cancellation and independent outcomes (A01-04)

The service exposes independent dimensions, each with monotonic `attempt_revision` **per attempt** and `status_revision` **per submission**: `dispatch_state` (`prepared→intent_persisted→transmitted→response_observed` or pre-dispatch `rejected`/`failed`; `transmitted→outcome_unknown→response_observed` is possible when a late result arrives; a known post-transmit error also records `response_observed` without a candidate), `delivery_state` (`none→candidate_delivered` if live/retained content delivered), `cancel_state` (`none→requested→confirmed` or `requested→unresolved`; unresolved may later confirm), `settlement_state` (`unsettled→provisional→final`, with later append-only reconciliation), and `generation_state` (`current→superseded` only by orchestrator authority). Repeated observations append higher revisions; no backward transition. `outcome_unknown` is an observation, never proof of stop; it can coexist with a conservative financial settlement. A late response may update attempt/usage records after cancellation or supersession, but never unconfirms a cancel or accepts the step. Cancellation before intent is `confirmed` only after durable proof that no intent/transmission occurred. After intent persistence but before transmission, preserve the append-only intent; confirm only after a durable no-transmit/cancellation disposition bars any later send and proves no transmission occurred. Until that proof, report `requested` or `unresolved`. After transmission, confirmation requires provider/transport evidence; authorization and intent alone are not transmission. Basic 1a statuses/cancellation are specified now; full 1b exposure/capacity holds and single-winner CAS remain separate proof (architecture §§8.4–8.5, 10.4).

`OutcomeEvent` is discriminated: `execution_observation` comes from gateway and names an attempt/transport fact; `step_evaluation` comes from authenticated orchestrator and names step/revision/generation plus candidate/attempt, `correctness` and independent `step_acceptance`; `task_outcome` comes from orchestrator and names task only, allowing abandonment before any step. A step rejection does not update task outcome; a task outcome does not retroactively mark each step correct. `event_id` is immutable. Each exact authenticated subject tuple in §9 has its own next positive `subject_revision`; after authentication and scope validation, an identical event ID/digest lookup returns its original durable `OutcomeAck` even if newer subject revisions exist. Same ID + different canonical event is `EVENT_CONFLICT`; a new ID with stale, skipped or duplicate revision is `STALE_REVISION`. `event_digest = SHA-256(UTF8(JCS(OutcomeEvent)))` after the same strict JSON input rules; it is an equality check, not caller authority. ACK is issued only after durable append, with event digest and recorded revision; lost ACK is recovered by authenticated `getOutcomeReceipt(event_id)`. The service records orchestrator assertions; the orchestrator's state store owns current-generation winner CAS and external effects. `step_evaluation.correctness:pass` alone is not task acceptance. A superseded result is billed even if never accepted (architecture §§8, 10–11).

## 5. Usage, cost and cohort accounting (A01-05)

`UsageRevision` is an immutable **replacement snapshot** for one `attempt_id`, not a delta. Revision 1 has no parent; each later revision names the immediately previous revision, increments by one, and appends with the same attempt. Exact repeat of revision ID/digest returns the existing record; conflict, skipped/self/stale parent rejects. The effective per-attempt view is the latest valid revision at a report cutoff. A task total sums each attempt **once** using its effective cost, including supporting, failed, abandoned and superseded attempts; settlement revisions are never summed together. If any cost is unknown, report a known subtotal plus unknown-attempt count, never label subtotal a full total. Task acceptance and cost remain independent. Raw provider usage is retained as a digest + secured handling-bound reference when permitted; it is not inserted unchecked into telemetry or a content-free ledger (architecture §§10.1–10.7, 13).

Each normalized category (`input_uncached`, `input_cache_read`, `input_cache_write`, `output_text`, `output_reasoning`, `other_billable`) has `state:known` with nonnegative safe-integer count, `unknown` without count, or `not_applicable` without count. The usage-semantics version maps every provider unit to exactly one category: uncached input excludes cache reads/writes; cache writes are counted once at creation; output reasoning excludes output text; a provider-specific component enters a uniquely named `other_billable` item. `other_billable:[]` means no such component is reported under that version; if one may exist but its amount is unknown, include an `unknown` item. `not_applicable` needs a versioned provider-semantics reason, never a guessed zero. Partial known counts are retained without filling unknown categories with zero. `usage_observation` is `unknown` when no applicable count is known, `partial` when known and unknown coexist, `reported` when the applicable provider counts are known, `estimated` when any count is inferred, and `reconciled` for later corrected evidence. `cost.status` independently is `unknown|reported|calculated|estimated|reconciled`. An estimated usage category needs a method reference; an estimated cost requires method and inclusive lower/upper bounds, verified numerically. A cost of zero is allowed when reported/calculated/reconciled with `zero_basis` evidence, even if token counts are unknown; unknown cost has no amount. Price version and usage-semantics version are mandatory for every revision. Provider-reported processing region is recorded when available, not invented.

**Proposed money wire policy:** ISO 4217 three-letter currency; nonnegative exact decimal string, no exponent/plus/negative zero/leading zeroes, at most 9 fractional places, canonical shortest form. Conversion to 9 places uses decimal round-half-even and records price version; no FX combination across currencies. Corrections replace an effective snapshot and may reduce its amount; negative amounts/refunds require a separately approved adjustment type, not a hidden negative usage revision. For complete cohorts, reports retain failed/abandoned tasks and all supporting calls; no terminal success is copied onto preceding step verdicts (architecture §§10–11).

## 6. Validation order, capabilities and handoff (A01-06, A01-07)

For an HTTP call, routing/version header then authentication/scope check precede body parsing to avoid leaking details. For an authenticated caller, order is: strict UTF-8/JSON parse (`MALFORMED_JSON`, 400), entrypoint shape and bounds (`SCHEMA_INVALID`/`LIMIT_EXCEEDED`, 400/413), semantic cross-field and source/prompt/reference checks (`SEMANTIC_INVALID` or `SOURCE_INVALID`, 422), policy/approved configuration/spend (`POLICY_DENIED`/`FINANCIAL_AUTH_REQUIRED`, 403/503), capability (`CAPABILITY_UNSUPPORTED`, 422), then internal plan/FDC/intent (`PLAN_INVALID_OR_STALE`/`FDC_REJECTED`/`INTENT_PERSIST_FAILED`, no transmit). Authentication failure is 401; authenticated lookup outside scope is indistinguishable 404 `NOT_FOUND_OR_FORBIDDEN`. Unknown internal-only fields in a public request fail shape; a raw forged client plan never reaches FDC. Ambiguous transport outcome is an SDK `TRANSPORT_OUTCOME_UNKNOWN`, not a server response. The [vectors](DURANKI-WP-A-VECTORS-v0.3-CORRECTION-01.json) name the earliest intended layer and all preconditions for later-layer cases.

Initial `requested_features` is the exact sorted union of server-derived content features and caller-requested optional capabilities: the server derives `text` from text blocks, `tools` from any tool definition, tool-call/result block or non-`none` choice, `document_text` from any reference block, `nested` from parent lineage; missing derived flags reject `SEMANTIC_INVALID` before capability admission. Extra recognized flags are explicit requests and still undergo capability/policy checks; unknown flags fail shape. Initial `requested_features` can name `text`, `tools`, `document_text`, `background`, `nested`, plus explicitly recognized but disabled `streaming`, `realtime_voice`, `binary_multimodal`, `responses_web_search`, `provider_managed_state`. Tool-choice `required` is enabled only for a configuration whose pinned adapter preserves it; otherwise `CAPABILITY_UNSUPPORTED`. ## 7. Public read, failure and wait rules (A02-01)

The public accounting surface is `CandidateResult.usage` for a delivered result and `AttemptSnapshot.usage` in `getStatus`; no separate ledger route is proposed. `PublicUsageView.not_recorded` has no revision and means none durably existed at that response cutoff. `PublicUsageView.available.revision` is the latest durable replacement snapshot for its attempt at `StatusSnapshot.updated_at`; its `unknown` usage/cost states are explicit facts, not missing data. Later reconciliation increments the attempt and status revisions and becomes visible on an authorized later read. Raw provider report digest and secured reference remain internal; `PublicUsageRevision` omits both. Status authorization applies before lookup and again before content/usage projection. `TR-ACCOUNTING-PUBLIC` and `V-PUBLIC-USAGE-*` show the public path and forbidden read.

`submit(..., {wait_ms})` accepts only the one option defined in §1; the SDK emits `Duranki-Wait-Ms` even for zero, so server and client wait choices are observable. The server rejects malformed or out-of-range wait input with 400 `SCHEMA_INVALID` before admission. It never extends the signed per-attempt timeout or deadline. A 202 means the response wait ended, not that execution stopped. If FDC/intent failure becomes durable before wait expiry, HTTP 409/503 respectively carries `SubmitReply.failed`; the SDK raises `DurankiError` with its `handle`, `attempt_id`, `failure_stage`, `error` and `work_key` available for `getStatus`. On an HTTP 202 the SDK returns the typed pending reply, including its handle and `pending_result_policy`. A lost HTTP response raises `TRANSPORT_OUTCOME_UNKNOWN` and exposes the original caller-known `WorkSelector`, with no automatic resubmit. Status query failure uses `ErrorResponse`, never a fabricated `StatusSnapshot`. A stored terminal error on the polling path is carried by `StatusSnapshot.terminal_failure` together with `terminal_attempt_id`; it is safe and correlation-bearing and never includes prompt, output, raw usage or credentials. A query-service outage remains an `ErrorResponse` without a stored-work claim. `TR-PENDING-FDC-FAIL`, `TR-PENDING-INTENT-FAIL` and `TR-LOST-REPLY-FAIL` distinguish these branches.

## 9. Cancellation and outcome namespaces (A02-03)

`CancelSelector` is an explicit union. The ID path takes a body selector containing only the same `submission_id`; the by-work path takes exactly the four `WorkSelector` fields matching the path. Cross-form or mismatched path/body rejects `SEMANTIC_INVALID` (422) before state change; out-of-scope identity remains indistinguishable 404. A confirmed `CancelAck` requires `cancel_disposition` and `cancel_evidence_ref`: `no_intent` proves neither durable intent nor transmission, `intent_no_transmit` retains the intent and cites a durable no-send disposition that prevents future transmission, and `provider_confirmed` cites provider/transport stop evidence after transmission. A status attempt with confirmed cancellation carries `cancel_evidence_ref`. Without the applicable proof, report `requested`/`unresolved`; a transmitted unknown outcome remains billable and may settle later. `TR-CANCEL-TIMING` represents separate branches, not a single sequence.

Event-ID uniqueness and lookup use the authenticated namespace `(trusted principal_id, event_id)` across all three kinds; the client cannot supply the principal namespace. The writer for `execution_observation` is the gateway's internal append authority bound to the attempt; `step_evaluation` and `task_outcome` require an authenticated orchestrator with task scope. Subject revision counters are independent exact tuples: execution `(principal_id, attempt_id)` with generation verified against the attempt; step `(principal_id, task_id, step_id, step_revision, execution_generation)` with attempt/candidate verified against that generation; task `(principal_id, task_id)`. Revision 1 starts each tuple, including gen.2 after gen.1; later records increment by one. Authentication, role and scope checks happen first, then existing `(principal_id,event_id)` lookup: identical canonical event returns its original durable receipt even after later revisions, changed event conflicts, and only a new event ID undergoes subject next-revision validation. An out-of-scope or cross-principal receipt lookup is indistinguishable 404; a separate principal may reuse the same event ID in its own namespace. A step verdict remains independent of task outcome, and these append rules do not assert full-1b winner CAS or distributed recovery. `TR-OUTCOME-NAMESPACE` and `V-OUTCOME-*` are synthetic data cases only.
