# Duranki WP-A Contract Candidate v0.1

**Status:** `PROPOSED_FOR_WP-A/A2_REVIEW`; no DEC-04–08 adoption or runtime qualification. **Scope:** an initial, non-streaming, fixed-approved-destination Phase 1a profile and named later guarantees. This document is read with [schemas](DURANKI-WP-A-SCHEMAS-v0.1.json), [vectors](DURANKI-WP-A-VECTORS-v0.1.json), and [decisions](DURANKI-WP-A-DECISIONS-v0.1.md). The JSON schemas are candidate wire shapes, not a security policy or service implementation.

## Authority and surfaces

**Baseline (B):** architecture v1.1 §§5, 8–11, 13, 16 controls admission, binding, dispatch, accounting, and ownership. **Adopted package boundary (A):** Implementation Plan v0.2 §§1, 4 and WP-FND acceptance establish separate Python server, Python network client, and plain CommonJS JavaScript network client; their `0.0.0` packages are inert. **Source observation (O):** `mach-recce/` is a static Mach-Platform snapshot, not live integration proof. **Proposal (P):** everything labelled candidate or recommended here and in the schema bundle requires WP-A/A2 approval.

| Surface | Producer and consumer | Authority |
|---|---|---|
| `SubmitRequest` / `SubmitAck` | Trusted orchestrator through either SDK to service | SDK validates shape and transports; server independently authenticates principal, validates caller's task/charging authority, classifies, admits, and returns acknowledgement. An ACK means receipt or rejection, never dispatch or task acceptance. |
| `StatusQuery` / `StatusSnapshot`; `CancelRequest` / `CancelAck` | Authorized caller to service | Query and cancellation require authenticated task/generation access. A cancel ACK means request recorded, not provider stop. Status is a snapshot with monotonic service revision, not a winner decision. |
| `OutcomeEvent` / `OutcomeAck` | Authorized orchestrator to service | Orchestrator owns substantive step correctness, task acceptance, checkpoints, authorized generation, and side effects. Service records the event for accounting; it cannot infer acceptance from provider delivery. |
| `ExecutionPlan`, `PreparedCandidate`, `DispatchIntent` | Trusted optimization/admission/gateway components only | Never client-submittable. The optimization layer signs a work-bound plan using a gateway-held key; gateway checks and durably records intent. Examples contain no real signature. |
| `AttemptRecord` / `UsageRevision` | Gateway/accounting and provider report | Gateway owns attempt ID; provider request ID is reconciliation data, not an authority token. Ledger is append-only, independent of trace sampling. |

**Proposed endpoints** (transport names, not implemented routes): `POST /v1/submissions`, `GET /v1/submissions/{submission_id}`, `POST /v1/submissions/{submission_id}/cancel`, `POST /v1/outcomes`, `GET /v1/capabilities`. Every request carries `contract_version: "0.1"`; unknown major versions fail closed with `UNSUPPORTED_VERSION`. A capability response reports profile/version and supported features but does not override admission. Idempotent transport retry uses the same submitted generation and canonical work, never a new semantic attempt. Network timeouts leave receipt/dispatch unknown until status is checked; SDKs do not silently resubmit with a new generation.

## Shared field contract

`R` = required, `C` = conditional, `O` = optional. `1a` applies to initial profile; `1b` names later guarantees. All string IDs are opaque, nonempty, bounded strings; no client field conveys authority merely because it exists. Unless specified, missing `R`, invalid values and unknown non-version enums produce `SCHEMA_INVALID`; an unsupported contract/profile version produces `UNSUPPORTED_VERSION`. Missing `O` differs from explicit `null` (null is rejected). Proposed minor versions can add optional fields, never silently change old field meaning. Content and derived fields inherit combined source restrictions (architecture §§5.1, 13).

## DEC-04: work representation and dispatch binding

**P:** represent a request as ordered message objects, each with ordered blocks and stable lineage IDs. A `system` block identifies the trusted instruction source; a conversation turn identifies its role; content and tool-result blocks carry source labels, not just enclosing message labels. `tool_call` and `tool_result` IDs are paired and unique within the request. `resolved_prompt` holds stable prompt identifier/version **and the resolved text/hash**; the chosen model/deployment and generation settings are explicit. An adapter must preserve meaning or reject. See schemas `$defs/SubmitRequest`, `Block`, `Reference` and vectors `V-CAN-*`, `V-TOOL-*`, `V-REF-*`.

**P canonical wire rule:** JSON objects have unique keys; UTF-8 valid Unicode scalar strings are used without Unicode normalization; arrays preserve order. Reject duplicate keys, invalid Unicode, NaN/infinity, floating-point canonical-work numbers, negative zero, and unknown semantic fields. Use integers only within the interoperable safe integer range; represent money and nonintegral settings as decimal strings without exponent. Normalize decimal strings before the work projection to shortest exact base-10 form (strip insignificant trailing fractional zeros and a now-empty decimal point); reject any negative-zero spelling. The schema checks lexical shape; this numeric normalization and uniqueness check are semantic validation. Omission is distinct from null, and null is rejected unless a field explicitly permits it. The canonical projection removes only declared nonsemantic trace IDs and observation timestamps; it retains deadlines, timeout settings, prompt/model identity, source labels, references, tools, blocks, and generation settings. Serialize the projection with an RFC 8785/JCS-compatible key-order and string escaping profile, then compute `SHA-256("duranki-work-v0.1\n" || UTF8(canonical_json))`. RFC 8785 is a **standards-basis proposal**, not a claim that a validator or implementation was executed here; approval must pin test vectors and any interlanguage edge cases. The server recomputes; client hashes are hints only. Logical identity `(principal, task_id, step_id, step_revision, execution_generation)` with equal server work hash is a duplicate candidate; unequal hash is a conflict. Domain and version prevent reuse across projections.

**B sequence:** canonical pre-adapter work → signed plan bound to that work → deterministic candidate preparation for the named deployment and adapter version → FDC **after** every callback/transformation → durable dispatch intent (authorization point) → transmission → append-only settlement. FDC checks current policy/recovery/registry versions, signature/expiry/revocation, exact prepared binding, current classification and combined restrictions, current destination approval, applicable capacity/financial authorization, and deadline (§5.4). Persist failure means no transmit. Revocation before intent prevents authorization; revocation after intent and before transmit requires recheck; an already transmitted attempt cannot be recalled and must settle. Classification snapshot is audit data only. WP-B must prove the prepared-request binding subset—ordered content, labels, tool definitions/choice and IDs, resolved prompt/model, references, settings, adapter version, candidate destination, and signature/version checks—at the actual pinned gateway/independent receiver boundary. A raw client mutation is only a preliminary negative case; a controlled post-binding callback mutation is required for T-09.

## DEC-05: identity, state and outcomes

**B:** orchestrator creates logical `step_id + revision` and `execution_generation`; gateway creates `attempt_id`; provider may return its own ID. The same generation and same work is deduplicated under the full profile; same generation with different work conflicts; a newly authorized generation is a distinct escalation. The initial 1a interface reports these identities and should reject a local conflict, but does **not** claim durable cross-replica exactly-once deduplication, atomic shared retry budget, single-winner CAS, or hard exposure ceilings. A timeout is `outcome_unknown`, not authorization for SDK semantic retry. See architecture §§8.2–8.5, 10.4, 16 T-10–24.

**P state vocabulary:** submission `received | rejected | admitted | no_route`; attempt `prepared | fdc_rejected | intent_persisted | transmitted | response_received | outcome_unknown | cancel_requested | cancel_confirmed | failed_before_dispatch | settled`; delivery `none | candidate_delivered`; structural verdict `not_checked | pass | fail`; orchestrator step verdict `pending | accepted | rejected | superseded`; task outcome `open | accepted | failed | abandoned`. State snapshot carries `status_revision`, `updated_at` and distinct attempt records. A late result from a superseded generation can be delivered for reconciliation and billed, but is never reported as accepted merely by the gateway. The full 1b orchestrator state store commits the first verified result from the **currently authorized** generation by CAS; an earlier generation's result never wins after supersession. In 1a, this is a required future contract, not a proven service guarantee. `CancelAck.requested` means cancellation was requested; `confirmed` needs provider/transport confirmation; `unresolved` preserves possible remote execution and unknown usage. SDKs must surface these states, not map them all to one retryable error.

**P error categories:** `SCHEMA_INVALID`, `UNSUPPORTED_VERSION`, `AUTHENTICATION_FAILED`, `AUTHORITY_INVALID`, `CLASSIFICATION_REQUIRED`, `HANDLING_CONFLICT`, `DESTINATION_FORBIDDEN`, `CONFIGURATION_NOT_APPROVED`, `CAPABILITY_UNSUPPORTED`, `WORK_CONFLICT`, `PLAN_INVALID_OR_STALE`, `FDC_REJECTED`, `INTENT_PERSIST_FAILED`, `TRANSPORT_OUTCOME_UNKNOWN`, `CANCELLATION_UNCONFIRMED`, `USAGE_UNKNOWN`, `INTERNAL_UNAVAILABLE`. Each response includes safe code, correlation ID, retry guidance (`never`, `same_generation_after_query`, `orchestrator_decision`), and no sensitive payload echo. Only server policy decides admission; SDK exceptions mirror response categories.

## DEC-06: capability and handling profile

**P initial slice:** synchronous non-streaming text; structured tool calls/results with source labels and paired IDs; `auto`/`none` tool choice, with `required` only where an adapter proves it remains required; caller-owned structured interpretation of text/tool output (including JSON salvage); materialized document **text** or immutable/versioned references; named service principal plus charging owner for background work; nested calls as separate authorized, inherited-policy requests; missing usage as unknown. Fixed requested destination must be approved in the Phase 1a file. All enabled paths still require Phase 1a identity, purpose, handling/retention, destination permission, spend limits/alerts, FDC and intent. Metadata migration is explicitly flagged, accounting/analytical only. No concurrent hard-ceiling guarantee and no model substitution (§5.1).

**P explicit pre-dispatch rejection:** streaming, realtime voice, audio/image generation, binary multimodal payloads, direct Responses/web-search state semantics, and uncontrolled provider-managed mutable state. They remain later architecture candidates; enabling one earlier triggers its first-relying-phase tests. A non-streaming analogue does not verify a source streaming workflow. Source cases: `lib/vega-chat/dispatch.js:194-235`, `lib/vega-realtime.js:4-21`, `lib/numerics-tier2/providers/xai-web-search-adapter.js:30-68` (static recce mapping). Do not infer provider support from those call sites.

## DEC-07: usage, cost and outcome reporting

**P:** every attempt records raw provider usage (or explicit absence), mutually exclusive normalized categories (`input_uncached`, `input_cache_read`, `input_cache_write`, `output_text`, `output_reasoning`, `other_billable`) in integer units; an `other_billable` item names its unit and provider component so it cannot hide overlap. Category partition rules, `usage_semantics_version`, `price_version`, currency and decimal monetary strings are explicit. `usage_status` is `unknown | reported | calculated | estimated | reconciled`; unknown contains no invented zero. Estimates state method/bounds; reconciliation appends a linked revision and preserves prior raw report. Amounts are decimal strings with sign/scale rules in schema, avoiding binary floating point and choosing no database. Separate dispatch, delivery, structural status, step verdict and task outcome lets later complete-cohort reports count failed/abandoned tasks and supporting calls. A terminal accepted task does not confer correctness on every earlier step. Content/derived features remain subject to architecture §13 retention; ledger contains no raw content by default.

## DEC-08: clients and adapter handoff

**A:** `server/`, `clients/python/`, `clients/js/` remain separately packaged, with JS CommonJS and no Python import dependency. **P:** future public root exports are `DurankiClient`, typed request/response/error values and `getCapabilities`; Python analogues live in `duranki_client`, never import `duranki_server`. Protocol major and capability profile are negotiated explicitly; minor additions are optional and ignorable only if nonsemantic. Installed clients must produce equal server-interpreted work on shared vectors, preserve rich attempt/usage/outcome fields, and expose typed errors. Current `0.0.0` foundation modules do not provide this API.

**O, not accepted behavior:** static Mach-Platform recce saw tool-choice weakening/schema normalization/cache-hint removal (`lib/vega-chat.js:195-239`), dynamic prompt/model resolution (`lib/vega-prompts.js:37-43,109-126`; `lib/vega-chat.js:123-158`), optional principal strings (`lib/vega-chat/dispatch.js:4-17`), and missing usage replaced with zero (`lib/vega-coding/xai-provider.js:75-82`). These are compatibility probes: a pinned adapter proves semantic preservation at the final request or the combination is rejected. Future Vega mapping must happen at its own trusted orchestrator boundary; no Proto object or source module is silently trusted or imported.
