## Scope, version selection and exact public surface

Wire `0.3` has capability `retrieval-synthetic@1`, operations `embedding.create@1` and `rerank@1`, projection `duranki-work-v0.3`, admission `dev12-admission@1`, plan `dev12-plan@1`, and usage `dev12-native-usage@1`. These are candidate identifiers. Wire `0.2`, its exact golden bytes/digests, text and caller-owned tool cycles remain untouched and are not reinterpreted by `0.3`. There is no gateway-issued retrieval, corpus ingestion, vector store or agent delegation action.

The public HTTP surface inherits the WP-A submission family and authentication, content type, non-enumerating status access and bounded wait semantics: `POST /v1/submissions`, `GET /v1/submissions/{submission_id}`, and `GET /v1/submissions/by-work/{task_id}/{step_id}/{step_revision}/{execution_generation}`. GET has no body; `StatusQuery` maps the client selector to one of those paths. The required `Duranki-Contract-Version` header is exactly `0.3` and must equal the JSON `contract_version` on submit; an absent/mismatched version returns HTTP 426 `UNSUPPORTED_VERSION` before admission. Status GET uses the stored submission version and the requesting client must explicitly accept it. Both GET paths are read-only and return a `StatusSnapshot` or `NOT_FOUND_OR_FORBIDDEN`. The public SDK's explicitly selected `submit_embedding` and `submit_rerank` mean one submission of a typed operation, returning a handle or typed result; `getStatus` does not submit. Existing client defaults stay `0.2`.

`wait_ms` is an SDK option mapped to exactly one `Duranki-Wait-Ms` header, integer 0…30000, default 1000 when omitted. It is not a query parameter. Duplicate/malformed headers reject before admission; wait starts after admission, is bounded by task deadline, and never lengthens the signed attempt timeout. Waiting does not create another attempt. HTTP 202 is `SubmitReply.pending` or a durably known `outcome_unknown`; HTTP 200 is `SubmitReply.completed`; HTTP 409 is a same-key conflict `ErrorResponse` or a known pretransmit `SubmitReply.failed`; HTTP 503 is a known pretransmit service/intent failure; HTTP 502 is a known posttransmit or result-validation `SubmitReply.failed`. Other pre-admission errors use the inherited 4xx categories. The returned handle and attempt ID remain available on pending, failed and unknown branches. Status GET returns HTTP 200 even for stored failed/unknown states. A transport failure with no received response is resolved by `getStatus` using the same full WorkKey before any new submission. A status read, refresh or retry of the exact work returns the existing submission and cannot reserve/send again. Unsupported but well-formed operation/profile is `CAPABILITY_UNSUPPORTED`; malformed envelope, operation shape or unknown field is `SCHEMA_INVALID`. Unknown version is `UNSUPPORTED_VERSION`. Unsupported handling or unregistered content/configuration is rejected pre-reservation as `SEMANTIC_INVALID`; it never falls back to another route.

The authenticated WorkKey is `(principal_id, task_id, step_id, step_revision, execution_generation)` for both versions. First look up that full namespace before creating an attempt. Same key/version/digest recovers existing state subject to **current** access controls; same key with changed caller assertion/content yields `WORK_CONFLICT`, and cross-version reuse yields `WORK_VERSION_CONFLICT`. `operation_id`, `submission_id`, `attempt_id` and `execution_generation` remain distinct identifiers. Recovery cannot revive revoked access, expired result content or an ineligible unsent plan; authorized historical handle and financial status remain readable after content expiry.

## Strict byte and shape boundary

The standalone decoder accepts only UTF-8 bytes, at most 262144 bytes, JSON whitespace bytes SP/TAB/CR/LF, at most 32 nested JSON levels, no duplicate keys after escape decoding, no unpaired surrogates, no non-scalar Unicode, no decoded U+0000–U+001F or U+007F in any string, and only safe integral JSON numbers. No BOM, invalid UTF-8, float, exponent-form number, unsafe integer, coercion or silent normalization is admitted. JSON integer `-0` is not separately adjudicated here; decimal coordinate/score **strings** do reject negative zero. The bounded schema walker uses own-property checks, including for `__proto__`, `constructor` and `toString`; those are unknown fields wherever `additionalProperties:false`. Local `$ref` resolution is only into this bundle's `$defs`. The checker covers each keyword this bundle uses, not arbitrary JSON Schema. Shape limits are combined with semantic constraints: ≤25 items/candidates, ≤8 delegation links, ≤2048 dimensions, IDs 1–160 ASCII characters, public text 1–4096 scalar characters, UTC whole-second timestamps that are real calendar instants, and decimal coordinate/score strings with ≤17 significant digits, exponent magnitude ≤100, |coordinate|≤1000000, no negative zero and score in [0,1]. Arrays retain order; object keys canonically sort ASCII lexicographically.

`RequestEnvelope` is a bounded discriminator for version and capability classification; only after its shape succeeds does version/capability selection occur. `SubmitRequest` then validates the selected typed operation. A semantic mismatch (registered profile, content, run, deadline, count) is `SEMANTIC_INVALID`. A malformed result or outer/result mismatch is `RESULT_INVALID`, independent of request admission. The byte-oriented negative corpus in vectors covers duplicate escaped keys, NBSP whitespace, invalid control escapes and surrogate failures; the checker also tests size/depth and hostile own properties.

## Fixed-public handling, authenticated context and canonical work

Candidate `0.3` permits only `public-synthetic-retained@1`: fixed synthetic texts whose `sha256(UTF8("duranki-public-text-v1\n" + text))` appear in the immutable registry fixture. The 256 KiB request, 64 KiB response, 5000 ms adapter timeout and seven-day retention limits are in the signed execution descriptor. Public synthetic request/result bytes may be retained for status/recovery for at most seven days, after which candidate bytes are unavailable and only permitted minimal audit/financial metadata remains under the existing record policy. No restricted, customer, credential-bearing, no-store, media or session payload qualifies. Reject unsupported handling/content before reservation or send. This profile does not change legacy no-store behavior and does not imply that production data may be retained in these ledger fields.

The trusted endpoint context is supplied by authentication, not request JSON. Its six identity fields (principal, actor, kind, charging owner, source authority, stable binding ID) are canonical server-supplied values. The allowed root, allowed initiating user, authenticated **current run ID**, authentication time and expiry are trusted admission context, checked but not copied into work beyond the six stable identity fields. The caller's root workflow, run, parent run, initiating user, ordered delegation links, declared reasons and optional commission are assertions in canonical work; they do not prove intermediate delegation. The current run must equal the trusted run. A direct human's actor matches the initiating user and has no links; a delegated agent's ordered acyclic link chain ends at the authenticated agent/current run and its parent equals the last predecessor; an autonomous service has no initiating human or links. Standalone admission records these links without asserting they were independently verified. No fabricated trusted run or intermediate actor is accepted to complete a fixture.

Commission absence stays **absent** in `metadata` and `CanonicalWork`. Explicit `{"kind":"omitted","reason":"..."}` or an asserted reference/reason are distinct canonical caller statements; null rejects. A missing commission may produce server assessment reason `caller_omitted`, but that reason is never inserted into work. Changing only the assessment leaves `work_digest` unchanged. Changing a caller declaration under the same WorkKey conflicts, even if the assessment is later identical. Current commission/authority requirements still gate recovery.

Embedding binds role document (1…25 items) or query (exactly one item), ordered IDs/text, and the **complete** registered compatibility tuple: `profile_id`, `model_ref`, `parameter_digest`, `dimensions`, `normalization`, `corpus_version`, `index_version`. The fixture uses `normalization:none`, since its vectors are not unit length. Rerank binds query, profile/corpus/index, ordered candidate ID/content version/digest/text and `top_k` ≤ candidate count. A candidate `content_digest` is exactly `sha256(UTF8("duranki-content-v1\n" + content_version + "\n") || UTF8(text))`; it proves correspondence to supplied synthetic bytes, not upstream corpus provenance. Caller owns indexing, retrieval and references. The registry fixture is synthetic and frozen for these checks; it is not a live provider catalogue.

`CanonicalWork` is the projection of accepted request fields plus trusted stable identity and full WorkKey, without server assessment. Its UTF-8 JSON has no whitespace, sorted ASCII keys, ordered arrays, minimally escaped strings and shortest integral numbers. `work_digest` is `sha256(UTF8("duranki-work-v0.3\n" + operation.type + "@" + operation.version + "\n") || canonical_bytes)`. A client-supplied digest is diagnostic only. The immutable `AdmissionSnapshot` has work digest, assessment time, commission evidence status/reason and delegation coverage. Its digest is `sha256(UTF8("duranki-admission-v1\n") || canonical_snapshot_bytes)`. This standalone fixture uses record-only commission and no verified intermediate links. Later evidence is a new linked event with source and time; it cannot rewrite caller assertions or an earlier snapshot.

## Signed plan, preparation and first write

The complete `SignedPlan` binds submission/attempt, work and admission digests, operation, adapter/destination, immutable price/usage references, financial owner, authority revisions, activation context, key ID/version, expiry, reservation and execution descriptor. Reservation binds budget account, financial owner, currency `USD`, price/usage refs and upward-rounded maximum exposure. The descriptor binds exact eligible `POST` route/host (`synthetic.invalid`), TLS trusted-sender transport, content type, adapter, preparation recipe digest, 5000 ms timeout, 262144/65536 byte limits, handling profile, 604800 second retention, one-attempt lifecycle and deadline. These are explicit immutable values, not unresolved bare IDs. The selected registry configuration resolves the adapter/destination and operation/role-specific price before signing. The stored admission bytes must recompute to the digest in the plan; the signed plan therefore authenticates its linkage to both work and assessment bytes.

The bounded preparation recipe is `{work_digest, operation, adapter_ref, route, handling_profile, timeout_ms}` in the vector. Its digest is `sha256(UTF8("duranki-preparation-v1\n") || canonical_recipe_bytes)`. The networkless worker receives only that plan-bound recipe and fixed-public candidate content, and returns exact proposed final request body plus method/host/route/headers/timeout/transport controls. The final guard must independently decode and compare the complete body to the admitted ordered request under the selected synthetic adapter and compare **every** control to the signed descriptor. Only the trusted sender can attach a credential and perform the first write; no worker path has a network interface or credential. An unrecognized adapter, destination, body or control is `FDC_REJECTED` with no fallback. This A1 vector proves binding arithmetic/signature shape, not that a runtime guard or sender already implements it.

Ed25519 signs the bytes `UTF8("duranki-plan-v1\n") || canonical_json(plan_without_signature)`; `signature` is unpadded base64url of the 64-byte signature. The fixture has a public SPKI key, exact signing-message bytes and one complete signed plan; no private key is stored. Every material field is covered, including activation, assessment, financial scope, reservation and destination. Routine key rotation changes minting, not verification: an old unrevoked key/version may verify its existing unexpired plan. Revocation makes an unsent plan ineligible even if cryptographically valid. At admission, prequeue, after any lower-layer wait and at first write, recheck expiry, authority vector, activation, permission/credential scope, price/usage eligibility and key eligibility. The standalone SQLite first-write ordering remains hold gate → atomically commit authority/audit/revisions → publish matching sender view → release gate → acknowledge; rollback preserves prior view, while committed-unpublished/uncertain update fails closed. Replicated/PostgreSQL publication is a later qualification, not a substitute for this ordering.

The fixed synthetic descriptor's `timeout_ms` is exactly **5000** in both schema and semantic comparison; a valid signature and recomputed recipe for any other timeout remain ineligible. The public `Duranki-Wait-Ms` response wait is a different clock and cannot change this signed adapter timeout.

For an unsent attempt, execution requires the conjunction of valid plan shape and registered semantics, recomputed work and admission snapshot bytes/digests, exact Ed25519 verification, and **independent current eligibility**. The bounded `ExecutionEligibilityContext` names expected submission/attempt, work/assessment digests, reservation/budget/currency/financial owner, activation state, every applicable current authority revision, evaluation time, send permission, plan revocation and verification-key records keyed by the plan's exact signed `(key_id,key_version)`. The verifier resolves that tuple from the context, rejects missing/duplicate/unknown/revoked keys or wrong SPKI material, enforces canonical unpadded base64url length and Ed25519 key type, and requires `evaluation_time < expires_at` (at expiry is ineligible). The context's active minting selector is recorded separately and does not decide an already signed version's verification eligibility. A synthetic tagged activation epoch must match independently; the standalone absent state remains valid when expected. The vectors use one unchanged signed plan to distinguish ordinary minting rotation from bound-key and plan revocation. These are offline decisions, not proof of a deployed key service.

Current permission to **send an unsent plan** is not authority to read historical status or record late usage. Once a submission has been admitted and possibly sent, authorized history uses its independently accepted stored work, plan and reservation identity plus current read/usage-write access, even after execution expiry or key revocation. Historical reporting never reopens the first-write gate, re-signs a plan, creates a reservation or releases unresolved exposure. No-repeat ownership still applies.

## Correlated results and native accounting

An embedding result matches the **outer** attempt, operation, registered profile/model/dimensions and has exactly one ordered vector for each input item, with matching index/ID/dimensions and valid exact decimal coordinate strings. A rerank result matches the outer attempt/operation/profile, contains exactly `top_k` distinct in-domain candidates, ranks 1…k, descending exact scores, and ascending input index for ties. Reply and status handles also match the independently accepted **submission ID** and full WorkKey; reply, status, usage and result attempt IDs all match the independently accepted attempt. The caller need not know a server-assigned submission ID before receiving its first reply; the server validator compares against its own admitted record. Invalid output never becomes a completed success; a failed validation may still retain independently observed usage and charge. Valid output may have unknown cost. No result is inferred from a caller lookup.

[Tariffs](tariffs.json) are **fictional** and not a selected commercial rate. The immutable [registry](registrations.json) binds rerank configuration A to `tariff.synthetic.a@1` with required `search_units=ceil(n/10)` and raw `max(USD 0.005, USD 0.003×units)`, and rerank B to `tariff.synthetic.b@1` with required `document_units=n` and raw `n×USD 0.0003000005` for n≤10 or `n×USD 0.0004000005` for the whole request when n≥11; both require one query and 1…25 candidates. Document embedding separately charges `document_units=n` for 1…25 items at fictional USD 0.000200000/item. Query embedding separately charges exactly one `query_units` at the same fictional unit rate. These four price contracts have explicit operation/role/component/domain/currency and immutable references; the bounded successor `ContractRef` permits `@1` without relaxing legacy `Id`.

Per-attempt raw money settles half-even to USD 0.000000001; reservation exposure rounds **up** to that quantum. Maximum single-attempt bounds: A USD 0.009000000, B USD 0.010000013, document embedding USD 0.005000000, query embedding USD 0.000200000. Three separate B one-document calls settle USD 0.000900000 and reserve USD 0.000900003; one B three-document call settles/reserves USD 0.000900002. The complete 1…25 A/B/document rows and query row are independently checked by Python `Decimal` as well as JS integer arithmetic. No call is authorized by a fictional price record.

Each `UsageRevision` binds attempt ID, ordinal/predecessor, immutable native-usage/price refs, exactly the selected operation's required component, presence and provenance, cost state and optional amount. A reported complete quantity must equal the admitted request's count/formula; a calculated amount must equal the selected exact tariff. `calculated` and `over_bound` require an amount; `unknown` forbids one. Missing, null, invalid, derived-only or contradictory zero evidence remains **unknown** for these synthetic contracts; expected input size is never silently promoted to reported usage. A reported amount above reservation is `over_bound` and remains visible; never clamp it. Later revision replaces the effective record only if predecessor and refs match; direct totals count each distinct attempt's latest effective settlement once. Preserve positive raw amounts that round to zero under DEV-11. Alternative actor/provider/workflow groupings and recursive inclusive workflow unions do not add charges.

`HistoricalUsageContext` is the bounded, independently supplied accepted record for the original work, admission digest, full WorkKey, signed plan digest, reservation/budget/currency, owner, immutable price/usage refs, read/write access and complete accepted usage revisions. It is verified against the original admitted request and stored plan with an **underbound-tolerant historical** check, not current send eligibility or a fresh-admission bound. Each accepted revision is a complete typed row for the same attempt, consecutive from 1; its predecessor points to the actual latest accepted ordinal. An initial row requires empty accepted history and no predecessor. An identical duplicate returns the existing accepted state without a second contribution; conflicting same-ordinal content, foreign attempt, missing/fabricated history, stale/forked/skipped/self/future predecessor or changed immutable refs rejects without changing state. A status displays exactly the latest effective accepted row; it cannot derive a prior row from its own public revision field. The pure reducer accepts only validated historical contexts, unions distinct attempt IDs and sums each latest known amount once, preserving unknown-attempt count. Actual observed charges above a historical reservation remain `over_bound` and visible even when that reservation would not qualify a new admission.

The offline `HistoricalUsageContext.accepted_revisions` representation is bounded to 32 rows. A new append is accepted only when its resulting context also satisfies the declared schema and historical semantics. At capacity, a new revision is rejected without modifying accepted history; an identical already accepted row remains a nonadditive duplicate, and a conflicting duplicate remains rejected. Status, the latest effective row and totals remain usable after rejection. This reference-context capacity is not a production lifetime or retention limit. Capacity rejection does not establish zero cost, discard an actual observation, release exposure or authorize resend; A2 storage must preserve genuine late financial evidence through its qualified representation.

## Status, errors and storage boundary

`SubmitReply` has `pending`, `completed`, `failed` and `outcome_unknown` branches with a common handle/attempt. `StatusSnapshot` carries submission state, monotonic status revision, bounded attempts, per-attempt dispatch/delivery/settlement, optional result/usage and explicit candidate access. `settlement_state:pending` means **no accepted effective usage row yet**; once one exists, the outer state must equal its `calculated`, `unknown` or `over_bound` cost state exactly. Unknown evidence has no amount and cannot be labelled over-bound; a known over-bound amount cannot be hidden as unknown. A known pre-send failure has no receiver arrival and no charge; an ambiguous post-send outcome retains reservation/exposure and forbids automatic resend. Invalid output with usage has failed delivery plus retained financial evidence; valid output with missing usage has completed delivery plus unknown cost/exposure. `ErrorResponse` includes `contract_version`, stable code, `correlation_id` and retry guidance (`never`, `query_first`, `after_replan`); do not expose credentials, full prompts or raw provider diagnostics. The exact HTTP/SDK implementation and wire tests are A2, not a claim of current support.

Completed valid delivery may have `candidate_access:expired` with **no result bytes** and unchanged handle, WorkKey, attempt and latest effective usage/amount. The independent `RetentionContext` states the prior result-availability origin, declared cutoff, observation time, result-was-available fact, access grant and expected submission/attempt. The cutoff is exactly `origin_at + 604800 seconds`; expiry applies at or after it. This content clock is separate from plan execution expiry. Before that cutoff, valid content is `present` with a result; `expired` before cutoff, expired-with-result, present-without-result and expiry without trusted retention context reject. Expiry cannot convert completion to failure, erase a calculated/over-bound charge, settle unknown to zero, release possible-send exposure or create another attempt. Pending, failed and unknown cases that never had result content have no invented expiry branch. Historical read authorization remains required.

An additive SQLite successor implementation later stores lossless canonical work, separate immutable assessment bytes/digest, signed plan/context, append-only verification events and native usage revisions with immutable price/semantics refs. Preserve existing `submissions`, `intents`, `guard_dispatches` and `usage_revisions`, old rows/digests/prices and their absence states. Restrict retained content to this fixed-public candidate; do not copy restricted payloads into ledger JSON. Incomplete status or an expired retained candidate must still expose permitted handle/attempt/financial state under current access controls. A2 migration/readback and A3 guarded target checks will prove runtime behavior; A1 has no database migration.
