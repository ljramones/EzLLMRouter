# Duranki external accounting integration contract v2

**Status:** focused successor to [v1](../integration-readiness-v1/CONTRACT.md). Select `/integration/v2/` and `Duranki-Integration-Version: 2`. The v1 routes, four v1 schema copies, released v1 archives and stored v1 records remain supported. Controlled-execution wire 0.2/0.3 and sender ownership are separate. This is an accounting and evidence transport, never model-call permission.

## Common authority and delivery

The v1 dataset/owner/ingest-principal binding, activated-at membership, account administration, bearer authentication, 65,536-byte request limit, strict JSON, exact-decimal strings, immutable event IDs, duplicate receipts, conflict responses and query-first telemetry recovery continue. A v2 event uses `integration_version:"2"`; a v1 event must use the v1 route/header. Existing v1 events remain readable after the additive SQLite migration. New v2 fields on old attempts are reported as absent or `legacy_absent`, never guessed. A delivery retry repeats the same event ID/body; a model retry is a distinct attempt.

IDs retain `[A-Za-z0-9][A-Za-z0-9._:-]{0,159}`. A path ID is one encoded segment, decoded **exactly once**, then validated; malformed escapes, separators and double-encoded separators reject. Timestamp fields require real Gregorian UTC seconds in `YYYY-MM-DDTHH:MM:SSZ`. An ID such as `event.TimeZ` is valid. `outcome` activity in v2 requires `outcome`; a previously accepted v1 outcome without it reports `not_observed` in JSON and CSV.

## V2 HTTP surface

The v1 method set is mirrored at `/integration/v2/datasets`, `/accounts`, `/accounts/{id}/state`, `/accounts/{id}/eligibility`, `/events`, `/events/{id}/receipt`, and `/reports/usage`. The authenticated owner/report scope also has `GET /integration/v2/reports/dataset?dataset_id=...`; it exports included attempts, related immutable event bodies, referenced eligibility answers and snapshots. The dataset ingest principal may `POST /integration/v2/snapshots` and retrieve its own snapshot at `GET /integration/v2/snapshots/{id}?dataset_id=...`; owner/report principals may retrieve/export within their owner scope. An export is bounded by the local HTTP/client response limits; pagination is not yet qualified.

## Identity and observed work

`attempt_started` adds a versioned `operation_family_version:"1"` and bounded `operation_family`: `generation`, `embedding`, `speech_input`, `speech_output`, `search`, `realtime`, `rerank`, `other`, `unknown`. This classification records the platform's reported operation; it does not claim adapter coverage. The actual Vega operation inventory is not verified by this contract. `model_identity_state` is `known`, `not_applicable` or `unknown`. `model_id` is required only for `known`; a model-less operation has no fabricated model ID.

Each attempt has `logical_operation_id` and `attempt_role` (`initial`, `retry`, `fallback`, `fanout`, `unknown`). Retry/fallback starts name `predecessor_attempt_id`; predecessor delivery may be late, and the report then says `pending_predecessor`. A single later `lineage` event may enrich an unknown start with retry/fallback/fanout linkage. The service rejects self-links, cycles, conflicting logical/task bindings and known cross-dataset predecessors. Parallel fan-out is recorded separately from causal retry/fallback. Every attempt retains its own effective charge, and inclusive run totals count each attempt once. Missing v1 lineage stays `legacy_absent`.

The unknown-only enrichment rule applies in **both arrival orders**: an accepted lineage claim constrains a later start's logical identity and requires that start's role to be `unknown`; a lineage arriving after an explicit-role start conflicts even if its predecessor is still missing. A late predecessor must match task and logical identity. Reports mark an older, already-accepted contradiction `lineage_status: "binding_conflict"` and use the immutable start role/predecessor instead of presenting the contradictory link as trustworthy. The export retains the original event bodies. No model attempt or charge is inferred from a lineage event.

A v1 start has no logical-operation or attempt-role assertion. It cannot satisfy a pending v2 lineage for the same attempt, and a v2 lineage cannot enrich an already accepted v1 start; the conflicting new event is rejected in either order. A v1 start without such a conflict remains valid. For previously accepted v1-start/v2-lineage contradictions, the v2 report says `binding_conflict` while leaving v1 role and predecessor absent. Admission validates the proposed event and its connected lineage relationships. An unrelated, already accepted contradiction remains visible in report/export but does not veto new work in the same dataset. A new event touching that inconsistent component still conflicts. Duplicate receipts and effective charges remain unchanged.

An authorized start naming an unregistered account is accepted as `unresolved`; it does not create an account or credential. A later owner registration and `account_resolution` event can confirm the *same reported ID* within the same dataset, without rewriting the start. An account in another owner/dataset cannot resolve it. Already-executed work with a disallowed model or subsequently disabled account remains recordable. A report labels registration timing and selection-time evidence; current account state alone is not a historical policy verdict.

## Usage and cost independently known

V2 `usage` has separate `usage_state` and `cost_state`, each `known` or `unknown`. Known native units require distinct `native_units` and `usage_provenance`; unknown units omit both. Known cost requires currency, exact amount, cost basis and price reference/version; unknown cost omits monetary fields. Cost may be known while unit detail is unknown, or units may be known while cost is unknown. A zero monetary amount requires `zero_basis`; missing evidence is never zero. A later version repeats retained known units and adds cost evidence as a new ordinal. Out-of-order revisions are retained, while only the latest contiguous ordinal contributes. JSON and CSV expose both states, units, provenance and effective cost without manufacturing a price or observation. The reported monetary subtotal remains a subtotal when unknown-cost attempts exist.

The v2 JSON/CSV attempt row explicitly exposes `usage_state` independently of `cost_status`. It is `known` or `unknown` from that attempt's latest **contiguous effective** v2 usage revision; it is `not_observed` when no revision is effective, including a gap before revision 1; and it is `legacy_absent` for a v1 start projected through the v2 report. Legacy absence does not overwrite the original v1 usage body. Dataset export keeps every immutable revision so a reader can derive the effective state. The bounded response enums are in the v2 schema and examples; these response definitions do not alter accepted event shapes.

## Selection evidence and policy-bound snapshots

V2 eligibility GET returns an immutable `eligibility_id`, evaluation time, account/model/revision, `usable`, reason and SHA-256 digest, and stores the answer under the authenticated dataset. A `decision` records `eligibility_evidence.status` (`verified`, `stale`, `denied`, `bypassed`, `unavailable`). The first three require that answer ID. `verified` binds an actual usable answer and its applicable account revision at selection time; `denied` binds a nonusable answer; `stale` binds a formerly usable answer whose revision had changed. The server compares account/model and timestamps. A decision is still distinct from later result, usage or outcome. The dataset export carries the exact referenced answer and selected action. This is evidence of the answer used, not proof Vega enforced it; enforcement is the following milestone.

The decision's `eligibility_evidence.status` is the **caller-reported** status and remains immutable. V2 report JSON/CSV also exposes `eligibility_assessment`; dataset export includes `eligibility_assessments` keyed by decision event and attempt. This server assessment checks the retained answer and named account revision. It is `verified`, `stale` or `denied` only when supported by that evidence; `binding_conflict` for a mismatched answer; `not_assessed` for a bypassed/unavailable answer; `missing` when no decision exists; and `legacy_absent` for a v1 decision. Where an eligibility read, decision or later account mutation shares the same second and ordering cannot be established, a usable answer yields `indeterminate`. The service accepts a structurally matching `verified` or `stale` caller assertion in that case but does not promote either assertion to an established verdict. Reports may revise the derived assessment from verified to indeterminate when a later delivered same-second account-history mutation is learned; the answer, decision and receipt remain unchanged. An unambiguously stale or denied answer still rejects an incompatible caller assertion.

`context_ref` and `decision_ref` identify separate `feature` and `decision` snapshots. A v2 snapshot records dataset/attempt identity, schema/producer version, provenance, source and availability times, classification, source expiry, retention cutoff, SHA-256 digest and one of `captured`, `not_collected`, `unavailable`; retrieval can later show `expired`. Captured feature content is only the fixed allowlist in the [schema](schema.json): categorical task/operation IDs, modalities, size with measured/estimated provenance, requested output/latency/capability constraints and versioned agent/policy/configuration IDs. Captured decision content is the selected account/model, policy and eligibility evidence. Raw prompts/responses, media, free-form payloads, embeddings, credentials and secret-bearing URLs are not schema fields. The source/availability times make later-derived features distinguishable from pre-call features; a decision snapshot available after the attempt start is rejected.

Every reference binds the exact dataset, attempt, snapshot ID and expected kind (`context_ref` to `feature`, `decision_ref` to `decision`). This constraint applies whether the snapshot or referring event arrives first. An absent target remains `missing` until supplied; a present incompatible target conflicts before acceptance. A previously accepted mismatch stays in immutable history but reports `binding_conflict`, with no borrowed digest or content attribution. Dataset export carries `snapshot_reference_assessments` for included attempts/decisions beside the original snapshots and events. Expiry removes content only; it does not repair an incompatible binding or alter accounting.

Captured content is kept separately from snapshot identity/metadata. At or after `retention_until`, the local service removes content, preserves its digest and reports `expired`; startup after a restore applies the same purge. A duplicate snapshot ID/body returns the original digest, while conflicting reuse rejects. Default local operation accepts captured **synthetic low-class** snapshots only, up to 397 days from source time and no later than any supplied source expiry. Real captured features require an explicit owner-adopted local policy file with bounded low/internal class windows and a source expiry. [The policy table](../../plan/DURANKI-INTEGRATION-FEATURE-RETENTION-POLICY.md) is proposed, not approval for live collection. Offline backup expiry/destruction remains an operator obligation.

## Compatibility and limits

The [v2 examples](examples.json) and [offline checker](check.py) exercise shapes and independent effective arithmetic. Service and installed-client cases exercise authenticated delivery, reports, exports, retention and migration. The local SQLite release remains loopback and unpaginated. There is no Vega exporter, real dataset activation, live account usability enforcement, production database qualification, model send or provider spend. DEV-12 `CT02-02b` remains open.
