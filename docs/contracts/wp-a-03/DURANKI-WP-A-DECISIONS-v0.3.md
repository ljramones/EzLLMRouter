# WP-A/A1 v0.3 Decision Recommendations

**Status of DEC-04–DEC-08: `PROPOSED_NOT_ADOPTED`.** Architecture v1.1 requirements and the accepted separate Python server, Python network-client and CommonJS JavaScript-client package boundaries remain controlling. The v0.1 review supplies findings and a separately attributed primary standards supplement; it does not adopt these replacements. See [contract](DURANKI-WP-A-CONTRACT-v0.3.md) and [vectors](DURANKI-WP-A-VECTORS-v0.3.json).

## DEC-04 — Canonical work and source authority

**Recommend:** exact `duranki-work-v0.2` projection in contract §2 and `CanonicalWork`, with stable semantic `context_id` across credential refresh, ordered typed blocks, pre-classification `InputPrompt.source_artifact_digest`, post-classification `ResolvedPrompt.resolved_digest`, resolved references, parsed tool arguments and restricted JCS serialization (contract §§2, 8; `D-*`, `G-WORK-LABEL-NORMAL`, `G-WORK-CLASS-UPGRADE`, `G-WORK-CONTEXT-REFRESH`). The server recomputes the domain-separated digest; a client digest is never authority. System origin is checked against a trusted prompt resolver, tool IDs and source labels against trusted source context, and current handling again at FDC. Golden vectors `G-WORK-*` are inert calculations.

**Baseline fixed:** architecture §§5.1, 5.3–5.4, 9 requires source taint, combined restrictions, work binding, deterministic adapter preparation, signed plan, current FDC and durable intent. **Alternative:** a binary canonical format could reduce JSON numeric ambiguity but increases two-language encoder surface; raw JSON string hashing cannot preserve semantic equivalence. **Open for A2:** endorse or amend the restricted JCS/UTC/decimal rules, stable context lifetime, prompt digest split, content-derived feature rule, registry namespaces, tool-schema subset and synthetic golden cases. Actual classifier, reference resolver, key trust and gateway proof remain unverified. Review 01 §7 cites RFC 8785 and JSON Schema Draft 2020-12 primary specifications; those references are supporting standards evidence, not a new architecture decision.

## DEC-05 — Result, state and outcome contract

**Recommend:** blocking non-streaming `submit` with a full `CandidateResult` in a 200 response, 202 pending with a handle, authenticated by-work status lookup with latest public usage and stored safe terminal failure, bounded `wait_ms` (default 1000, max 30000), and no automatic retry after ambiguous loss. Use independent attempt/cancel/settlement/generation dimensions and discriminated execution, step and task events. Only a durable outcome append earns `OutcomeAck`; caller-owned correctness, step acceptance and task outcome stay distinct (contract §§1, 4; `SubmitReply`, `StatusSnapshot`, `OutcomeEvent`, `OutcomeAck`; transcripts `TR-TEXT`, `TR-ACCOUNTING-PUBLIC`, `TR-PENDING-FDC-FAIL`, `TR-LOST-REPLY-FAIL`, `TR-CANCEL-TIMING`, `TR-OUTCOME-NAMESPACE`).

**Baseline fixed:** architecture §§8, 11 separates generation/attempt/provider IDs, substantive acceptance and full-profile single-winner CAS. **Alternative:** accepted-plus-polling is viable where all eligible content may be retained, but fails no-store result recovery; synchronous-only delivery lacks an explicit pending state for uncertain remote execution. **Open for A2:** approve exact timeout/retention/status behavior, explicit cancellation selector/proof branches, trusted-principal event namespace and revision-subject tuples. Full 1b cross-replica dedup, exposure holds and CAS need future proof; their names in this contract are not implementation evidence.

## DEC-06 — Initial capability and authorization profile

**Recommend:** `initial_1a@1` fixed approved configuration, non-streaming text, structured tool/result, materialized document text, background service principal and nested calls, with exact content-derived feature flags plus explicit optional requests; omission of a derived feature rejects before capability admission. Reject streaming, realtime voice, binary multimodal, direct Responses/web-search and mutable provider state before plan. `ExecutionPlan` requires approval, current classification evidence, effective retention, typed spend-limit authorization and no fallback; optional later fields have explicit phase dispositions (contract §§3, 6; `ExecutionPlan`, `SpendLimitAuthorization`; `V-CAP-*`, `V-PLAN-*`).

**Baseline fixed:** architecture §§5.1, 5.3–5.5 requires identity, purpose, handling, permission, spend limits/alerts, FDC and durable intent, with **no** Phase 1a hard concurrent-ceiling guarantee or model substitution. **Alternative:** a broader streaming/provider-state slice matches more static Mach-Platform shapes but incurs first-relying-phase lifecycle and authority proof; a text-only slice fails source-informed tool coverage. **Open for A2:** approve enabled feature set, content-derived flag rule, approved tool-choice subset, metadata migration codes and trust-context issuer contract. No cloud, provider, gateway release or identity product is selected here.

## DEC-07 — Partial usage and replacement accounting

**Recommend:** per-category known/unknown/not-applicable counters and independent usage/cost states, append-only linked **replacement** revisions, secured raw-report digest/reference, price and semantics versions, and a 9-decimal-place nonnegative currency amount with half-even derived rounding. The minimal public projection is `CandidateResult.usage` plus latest per-attempt `StatusSnapshot.attempts[].usage`; `not_recorded` differs from an available explicit unknown revision, and raw-report references remain internal (contract §§5, 7; `PublicUsageView`, `PublicUsageRevision`, `TR-ACCOUNTING-PUBLIC`). Effective task cost sums only the latest valid revision per attempt; unknown costs yield a known subtotal plus unknown count (contract §5; `CountKnowledge`, `NormalizedUsage`, `Cost`, `UsageRevision`; `V-USAGE-*`).

**Baseline fixed:** architecture §§10–11 requires raw and mutually exclusive normalized usage, missing never zero, complete cohorts including supporting/failed/superseded attempts, and separate acceptance. **Alternative:** amount deltas are compact but harder to reconcile without double-counting; all-required zero-filled category counters contradict unknown usage. **Open for A2:** confirm category partition per provider, public revision/cutoff visibility, currency/rounding/zero-basis policy and permitted secured raw-report handling. No database or billing product is selected.

## DEC-08 — Adapter and installed client compatibility

**Recommend:** frozen protocol `0.2` under route `/v1`, exact version header and envelope, explicit `initial_1a@1` capability response, equivalent future `DurankiClient` methods in independent Python and CommonJS packages, rich response/errors including a stored-failure handle and status-service distinction, and preserve-or-reject adapters. The gateway's expected bytes are regenerated from signed work plus pinned recipe and compared with observed final bytes after callbacks (contract §§1, 3, 6; `PreparedCandidate`, `ErrorResponse`; `V-FDC-*`).

**Adopted package fact:** WP-FND Acceptance 01 covers inert separate package roots only. **Static source observation:** reconnaissance mapping identifies dynamic prompt/model resolution, tool-choice/schema transformations, optional principal tags and zero-filled missing usage (`mach-recce/DURANKI-CLIENT-CONTRACT-MAPPING.md`); these are compatibility cases, not approved defaults or live-traffic proof. **Alternative:** shared private server modules or silent adapter normalization would simplify SDK code but break package isolation or binding meaning. **Open for A2:** approve method/export names, route/error mapping, `Duranki-Wait-Ms` behavior and the data-only synthetic payload/transport map; WP-B must establish actual pinned-gateway behavior, and WP-C installed-client parity remains untested.
