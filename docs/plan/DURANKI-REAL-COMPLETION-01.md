No public reservation-create operation is needed: Ma'at creates its reservation in its own DB. The initial common protocol uses a component-issued reservation ID for every controlled invocation; this is a **shared extension** for Ptah/Alexandria, paired with decision D1. Duranki mints the distinct `call_id`, `attempt_id` and internal `hold_id` only after authentication. Identifiers are opaque `[A-Za-z0-9][A-Za-z0-9._:-]{0,159}`, case-sensitive and never reused by their issuer. Decode route segments once; reject encoded separators, duplicate query keys, unknown fields and cross-scope selectors.

Exactly one `Authorization: Bearer <service credential>` and `Duranki-Contract-Version: 1.0` are required. An execution request also has exactly one `Duranki-Authorization: <compact JWS>` and `Duranki-Context: <base64url JCS context>`. Service credentials select a registered tenant, issuer and role; caller strings cannot select another scope. They are transport/service authentication, not policy-read authorizations. Component signing keys never become Duranki plan-signing keys.

POST bodies require `Content-Type: application/json`, exactly one decimal Content-Length and an exact-length read. Reject Transfer-Encoding, Content-Encoding, BOM, malformed UTF-8, duplicate decoded JSON keys, lone surrogates, nonfinite numbers, excessive nesting (>16), unknown fields and conflicting duplicate headers. Hash execution body bytes before parsing. No query parameters alter execution semantics. HTTPS termination must preserve body bytes and authenticated headers; no rewriting/compression middleware is in the qualified path. Responses include `Duranki-Contract-Version: 1.0`, `Cache-Control: no-store` and bounded JSON. Bodyless GETs reject nonempty request bodies.

### 3.2 Body bytes and immutable client preparation

Inference body, complete example, UTF-8 without trailing newline:

```json
{"messages":[{"role":"user","content":"Say yes."}],"max_output_tokens":16,"temperature":"0.0","response_format":{"type":"text"}}
```

Embedding body, complete example:

```json
{"input":["A passage."],"input_type":"document","truncate":false}
```

Inference messages contain only role and text. Allowed roles are system/user/assistant; there are no tool messages, metadata, job/corpus/artifact IDs, routing fields, model selectors, component reservation or accounting envelope in the body. The embedding role and exact ordered text are semantic input. Metadata belongs in authenticated context, below. A bounded JSON-schema output format is available for Ptah/Ma'at choices, judgments and spans; unsupported schema/features reject rather than being dropped. The 1.0 subset is recursive `type`, object `properties`/`required`/`additionalProperties:false`, array `items`/`minItems`/`maxItems`, primitive `enum`/`const`, integer-valued `minimum`/`maximum`, and string `minLength`/`maxLength`, within the schema resource's size/depth bounds. It excludes references, regexes, external resources and executable extensions. The service validates output shape; consumer anchoring/meaning checks remain consumer owned.

Bodies must contain no IDs minted by Ptah/Ma'at or Alexandria. The consumer's prompt/template and two-worlds cases prove that rule; Duranki cannot detect an arbitrary ID hidden inside free text without changing meaning. The serializer never inserts such IDs, and unknown metadata fields reject. Model names/generations are in authenticated context, not in these bodies. Equal payload/prompt bodies therefore hash identically despite different jobs, reservations, epochs or accounting labels outside them.

The Python API provides `prepare_inference(payload, context)` / `prepare_embeddings(payload, context)`, producing an immutable PreparedRequest containing private `bytes`, body SHA-256, canonical context bytes and context SHA-256. CommonJS provides `prepareInference` / `prepareEmbeddings` with equivalent methods. Convenience preparation uses RFC 8785 JCS and bounded schema validation; decimal temperature is a string and all request schema numbers are safe integers. A prepared-bytes form accepts already serialized valid UTF-8 JSON and preserves those exact bytes. Server acceptance does not require canonical whitespace/key order.

The caller supplies the prepared hashes/context to its component issuer, obtains a JWS, then calls `execute(prepared, authorization)` in either client. The client sends the same captured byte sequence it hashed—Python `content=bytes`, CommonJS a private captured Buffer, never a later `JSON.stringify` of a mutable object. CommonJS getters return copies; `Object.freeze` on a public Buffer is not sufficient. Snapshot/validate context and caller options too. No callback, mutation, redirect or retry may substitute bytes after authorization. Hash getters and bytes are not recomputed from caller objects. Signer custody belongs to the component/Proto, not the execution worker or Duranki client.

Matching client methods are `get_status`/`getStatus`, `get_reservation`/`getReservation`, `cancel_reservation`/`cancelReservation`, `read_ledger`/`readLedger`, `get_generation`/`getGeneration`, `begin_recovery`/`beginRecovery`, `get_recovery`/`getRecovery` and `complete_recovery`/`completeRecovery`. Control methods still require their distinct control credential/scopes; packaging a method never supplies that authority. Ledger iteration preserves snapshot/cursor identity and never retries execution.

The server computes SHA-256 over the entire exact received execution body and compares it to the token's lowercase hexadecimal `hash`. Whitespace, final newline, key order and Unicode normalization differences change the authorized hash. It may then separately derive canonical internal work from parsed operation + immutable caller assertions/trusted identity and sign admission/execution records. Exact inbound-body binding, canonical work binding and final provider-body binding are three distinct checks. No semantic reserialization substitutes for the first.

#### 3.3.1 Adopted attribution, assertions and trusted facts — C1

`attribution` is mandatory in the authenticated context and therefore protected by the component token's `ctx_hash`; no attribution ID is inserted into the inference body. The 1.0 object is `AttributionAssertions`: `envelope_version: consumer-attribution@1`, immutable `binding_ref:{id,sha256}`, typed `actor:{actor_id,actor_kind,actor_version}`, `charging_owner_id`, `invocation_mode`, `root_workflow_id`, `run_id`, ordered `delegation` (0–8 H-style links), optional `parent_run_id`, optional `initiating_user_id`, optional H-style `commission`, and optional per-field `caller_reasons` for initiating user/parent/delegation. IDs and reasons remain bounded by the schemas. A human has `actor_kind:human` and null actor version, without an invented executing agent; agent/service versions are registered non-null identifiers. The shared envelope is part of this operation successor, not deferred integration work.

Commission preserves H's exact distinction between an absent key, explicit `{kind:omitted,reason:...}` and `{kind:asserted,reference:...,declared_reason?:...}`. Null is invalid. Caller reasons use the closed set `not_yet_issued|not_applicable|caller_omitted|unavailable`; a reason remains an assertion, not proof or a permission waiver. No parser inserts an omitted commission, initiating person, parent, intermediate actor, or server-assigned reason into caller work. Empty, missing, declared-absent and unknown facts retain their distinct submitted meanings.

**Binding enrollment and immutable lookup.** `AttributionBindingRegistration` submits one `AttributionBindingContent`: tenant/issuer, stable trusted identity, invocation mode, root/current/optional parent run, optional permitted initiating user, initiating-person/delegation policies, bounded immutable actor/owner/workflow/person evidence references and validity window. Its `binding_id` is unique; server computes SHA-256 over JCS content. A duplicate identical registration recovers its record; same ID/different bytes conflicts. Registration requires the current scoped operator's independent actor-registration, financial-owner and workflow authority; arbitrary component JWS possession is insufficient. The declared initial source is operator-enrolled standalone registry records; qualified external issuers/Proto may be added later, but no live integration is assumed. Human/agent/run enrollment records and authority evidence must actually exist in the release fixture/profile.

The execution service resolves `binding_ref.id` only in its own durable tenant/issuer registry, verifies the exact content digest and principal/actor/version/root/run/owner comparisons, validity and current eligibility, and checks the underlying grants/evidence independently. No caller URL is fetched, no first-use binding is invented, and an unavailable mandatory binding/grant fails closed. Eligibility/revocation revision is a separate mutable authority record published under the existing fence; immutable content and its digest never change in place. Each workflow/run may have its own binding: **two people using the same component issuer and executing agent have distinct initiating-person/root/run assertions and corresponding bindings**, rather than a static issuer-to-agent inference. The registration/read/CAS routes above are included in D1, T2 and T4.

Direct-human and autonomous modes preserve the H successor's no-invented-identity distinction. The 1.0 `autonomous_service` invocation mode admits a registered agent **or** service actor under an independently authenticated service principal, with no initiating human or delegation links in this bounded mode; it does not relabel an executing agent as a service actor. Both autonomous actor kinds have fixtures and independently enrolled autonomous-mode bindings. Autonomous work is not an unknown initiator relabelled as autonomous. New 1.0 delegated metadata may honestly omit an initiating user with a closed caller reason, or retain omission as omission, **only** when actor, owner, workflow and every authority the call relies on are independently verified and the binding explicitly permits metadata-only uncertainty. Required human/delegation authority may not be replaced by `unavailable`, a partial chain or a caller signature. Unknown/record-only links remain outside verified-person/verified-delegation coverage. This adapts H's bounded shapes without weakening its mandatory current endpoint/owner authority.

**Work, assessment and activation have separate bindings.** `CanonicalConsumerWork` contains the complete authenticated WorkKey (tenant/issuer/reservation/job/principal/stable identity binding/source authority), lifetime-stable `TrustedIdentity` including actor/version and owner, exact request-body SHA-256, semantic input SHA-256 and the exact typed caller context/assertions with omissions preserved. An identity or name change cannot mint another effect for it.

Caller assertions cannot supply these server assessment fields. `SignedExecutionContext` separately signs `consumer-execution@1`, work/admission linkage, issuance time and H `ActivationContext` with `UTF8("duranki-execution-context-v1\n") || JCS(context)`. The internal signature key is distinct from component issuers; fixtures deliberately use separate published RFC8032 test keys. The existing complete internal plan still binds attempt/hold/descriptor and all release controls. Refused no-attempt calls have no fabricated executable context (`execution:null`).

Later verification appends a typed `VerificationEvent` with its own sequence, time and immutable source evidence linked to the original work/admission digest. The original admission snapshot is never rewritten. Assessments/coverage/server reasons and activation do not enter canonical work or logical-effect identity. An unchanged-assertion retry is still refused as replay/used-reservation under the new public one-use contract, while GET recovers the same call/attempt/hold and appended verification. Changed assessments or activation cannot create another effect, release exposure, bypass current authority, or turn uncertainty into no-send.

### 3.4 Results, status and errors

## 4. Reservation, cancellation, epoch and recovery semantics

### 4.1 Distinct identities and one-use admission

The component owns its reservation; Duranki does not create it remotely. Uniqueness is `(tenant, issuer, component reservation)` **across epochs**, not `(epoch, reservation)`. Restoring the component or presenting a later token cannot revive a consumed/cancelled reservation. A unique durable authorization fingerprint, immutable assertion/context hashes, call and attempt rows, applicable financial holds and ledger event are joined in one admission transaction. Competing different bodies under one reservation cannot create two owners or holds. Definite rolled-back transactions have no accepted effect; uncertain commits require reads and fail-closed recovery.

An exact accepted-token replay is refused (`AUTHORIZATION_REPLAY`). For a valid scoped new token under a used reservation, compare the immutable canonical assertions: changed work is `CONTEXT_CONFLICT`, unchanged work is `RESERVATION_USED`. Neither case creates an effect. Changing only server assessment/coverage or activation never changes that comparison. Same-work repeated POST is not the recovery API. This deliberately supersedes the old public resubmission behavior while retaining its substantive no-duplicate-effect invariant. G-01's separation of immutable assertions from changing server assessments remains: later authority assessments do not create false work conflicts or another logical effect. Recover through scoped GET by reservation/call, even after token expiry. A new financial hold is never created by a read.

Valid scoped requests that fail model/policy/input/budget checks get one durable refused record, marked definite-no-send, without spending capacity. Auth failures before valid scope/hash/epoch validation do not create tombstones. Cancellation can create a tombstone without a prior request; no fake call or spent amount is invented. Unknown reservation selectors are not automatically proof that a lost request cannot still arrive: cancel/fence it first, or complete the issuer recovery barrier/window before allocating replacement spending.

### 4.2 First-write ordering and durable acknowledgements

Adopt the proposed cross-component interpretation: **dispatch acceptance is the qualified positive first application-request write, not HTTP admission, queue insertion, plan commitment, TLS handshake, or provider billing.** Cancellation and current authority changes serialize with that boundary using architecture §5.4's single-process SQLite gate. This interpretation requires D2 approval; it does not weaken any existing current-authority check.

1. Outside the first-write critical section, prepare/validate the final request, perform signatures and resource waits, and durably establish a single dispatch commitment/ownership bound to the body/context, immutable generation and internal hold.
2. The sender takes the authority gate, checks a coherent current issuer epoch/barrier, component and internal signing-key eligibility, service/principal/grants, cancellation tombstone, generation/destination/family/tools policy, deadline and durable reservation coverage, then performs the qualified nonblocking first write. No resource wait, network lookup, callback or key-service call intervenes.
3. A would-block/no-acceptance result releases the gate and waits outside it; all freshness checks repeat. Positive partial acceptance consumes the only send authority. Only the suffix of that same attempt can continue; a new connection or replay is not authorized.
4. Cancellation takes the same gate, commits the tombstone, audit and revision atomically, publishes the matching sender view, then acknowledges. A queued committed-but-unsent call is blocked. A stalled transaction blocks sends; a definite rollback preserves the old coherent view. Uncertain commit/publication closes affected release until recovery.
5. If first write won, cancellation cannot recall it. Record `too_late` when positive write is known; record `uncertain` when a durable commitment/possible write survives without decisive evidence. Preserve exposure. A crash between commitment/positive write and its later observation must never become a false no-send acknowledgement or permission to replay.

`CancelAck` records a stable `ack_id`, original cancellation command ID, issuer/reservation, durable sequence, `disposition: prevented|too_late|uncertain`, dispatch evidence, `prevents_future_first_write: true` and financial state at acknowledgement. `CancelReply` separates that immutable receipt from current reservation/financial status and echoes the request's command ID. The statement concerns a **new first write**, not stopping an already-started suffix or recalling provider work. A before-use tombstone returns prevented with no fabricated charge. Repeating the same command returns its original receipt and current linked status without another financial mutation; repeating with a new command ID returns the existing cancellation identity plus current status. Reuse of one command ID with different content conflicts. Failed/uncertain persistence never returns a success acknowledgement.

This matches Ma'at AT-M2's one paid call when accepted first, AT-E20's wait for acknowledgement or expiry+margin and residual for an earlier accepted call, and AT-E28's cancellation arriving before a paused agent's first call. Ma'at still rejects late results at its own fence. Even when outcome is uncertain, an acknowledged tombstone fences every future first write; possible prior execution remains recorded and reconciled. Operator disable, component/internal-key revocation and epoch recovery can still block any unsent committed call.

### 4.3 Independent expected-epoch authority

A signed epoch claim is not proof that the epoch is current. Add a durable `issuer_state` controlled independently of inference tokens, keyed by tenant/issuer: expected epoch, monotone state revision, active/recovering/disabled status, registered clock margin, recovery ID, prior epoch, final session-end time, token deadline, and reconciliation receipt. Inference cannot register an epoch by first use or by signing a different value.

Initial registration uses scoped operator setup with an audited component-control assertion naming the Seshat commit-wait epoch/record. Subsequent transitions use the separate `issuer.recover` credential registered for that component's recovery leader. Duranki authenticates that authority and CAS revision; it does not infer or independently fetch Seshat state, or claim to validate Ma'at's database capability. The component must authorize the call under its actual recovery capability. This explicit trusted control assertion/hook is an additional cross-component contract, requiring D3 approval.

`BeginRecovery` names expected revision/current epoch, a new never-before-used epoch, immutable recovery ID, final session-end Unix milliseconds, and token deadline exactly `session_end_ms + 60000`. Record registered margin and provenance of the epoch assertion. The first call establishes an issuer-wide admission/first-write barrier and publishes it under the fence before acknowledgement. Old and new epoch execution tokens both reject while recovering. Already-transmitted calls and usage corrections remain in the independent Duranki ledger. Same recovery ID/content returns the same receipt; conflicting content rejects. A new Ma'at recovery attempt cannot reset/extend the original recorded deadline; restart resumes the existing record.

Ma'at's required procedure remains: stop issuers/processes and DB sessions, record the **last session's end**, allocate the new history epoch, preserve its deadline through interrupted recovery, wait 60 seconds plus registered margin, reconcile Duranki's independent ledger, then resume. The Duranki begin hook runs while the component's recovery barrier is in force and before any ordinary issuer is enabled. It can fence early but cannot shorten the required wait.

`CompleteRecovery` requires the same recovery ID/new epoch and current issuer revision, server time at or beyond recorded deadline+margin, a complete scoped ledger snapshot and its sequence/digest, and an authenticated component reconciliation receipt after recording loss-window calls/exposure against original engagement/budget IDs. Require the server-issued `complete_snapshot_receipt` for this recovery and refuse a stale snapshot if relevant ledger changes occurred before the completion transaction; allow reads and reconciliation to catch up without executing anything. A completion retry returns the original receipt. Under the gate, commit and publish the active new epoch before acknowledging; never reactivate an old epoch. Only then may the component clear its own barrier and issue new calls. Duranki cannot certify the consumer's DB writes merely by accepting its receipt; consumer restore probes verify those writes.

Wrong-epoch conformance uses the current registered epoch, not token self-comparison. Tests include a correctly signed token from the wrong epoch, old-token delayed presentation after recovery, a token issued between restore start and the last terminated session, an interrupted recovery preserving the deadline, stale control revisions, and an unauthorized worker attempting a transition. Ma'at AT-R8 remains based on session-end expiry; the extra registration mechanism makes expected-epoch refusal concrete without claiming the original design specified this API.

### 4.4 Ledger and financial recovery

The independent ledger records every consumed authorization/refusal/call, component reservation, job, history epoch, generation, authenticated engagement/budget, internal hold/attempt, inbound/context/final-body hashes, state transitions, cancellation receipts, actual-model report, native usage revisions, immutable price basis, settled amount, held exposure and unknown/over-bound reason. It stores no provider credential or raw JWS. Do not retain prompt/input content merely to enable accounting.

`GET /api/v1/ledger` returns at most 200 rows with opaque cursor bound to tenant/issuer/filter/snapshot, `snapshot_id`, `as_of_sequence`, snapshot digest, complete-prefix/earliest-supported sequence, and next cursor. Stable snapshots include consistent effective call/usage state; later corrections appear at higher sequences. Export uses the same scoped/filter/snapshot set, without duplicate charges. The digest covers canonical data, not mutable response envelopes. Authenticated readers cannot widen scope through engagement/budget filters. Recovery scans the complete relevant history, not only rows the restored DB remembers or an unreliable client timestamp. A retention gap explicitly fails reconciliation.


**Whole-issuer recovery is not a filtered report.** LedgerPage now identifies tenant/issuer, `selection:whole_issuer|filtered`, snapshot row count, page offset and optional `complete_snapshot_receipt`. A recovery-scoped unfiltered read (`recovery_id` query) uses a server-side snapshot registry bound to issuer, recovery, normalized filter, high-water mark and digest. Only completion of the entire sequential cursor/page chain for the unfiltered whole-issuer snapshot yields its durable complete receipt; filtered/after-window or incomplete reads never do. `CompleteRecovery` must name that exact receipt, snapshot/digest and high-water mark; the server validates its own registry state, full coverage/retention and current relevant ledger sequence, not caller completeness flags. A filtered or incompletely paged snapshot cannot qualify even if its own prefix is internally consistent. L01–L04 and S05 cover shape and implementation obligations; server-side filter/page-chain/current-sequence checks remain runtime cases.

**Lossless attribution/report linkage.** Each CallStatus and call-linked LedgerRow retains `AttributionRecord`: exact canonical caller assertions (including omitted versus declared fields), stable TrustedIdentity, work digest, immutable signed admission bytes/digest/signature, signed execution/activation context when applicable, and linked append-only verification events. Pre-use cancellation/issuer administrative events may have null attribution rather than invented people/attempts. Retain lossless standalone SQLite records and an explicit PostgreSQL migration representation without qualifying production PostgreSQL here. Read/query/export filters include principal, executing actor/version, initiating user, charging owner, root/current/parent run, invocation mode, commission and verification status under existing read scopes. No raw prompt or private key is required for these joins.

Direct cost uses each actor's unique attempt once, delegated cost its descendants and inclusive cost the set union of direct+descendant attempts. Use latest-effective usage revisions once; do not sum repeated ledger events, nested inclusive totals or overlapping workflows. Verified person/lineage reporting uses independently verified bindings/edges; show asserted/partial/unavailable coverage separately and do not launder it into verified totals or access. Unknown initiating person differs from proven autonomous work. Two initiating people through the same issuer/agent remain distinguishable in person/root/run views, while one underlying attempt remains one expenditure. Operator drill-down and JSON/CSV/export preserve the assertion-versus-assessment and native usage knowledge axes separately.

For the initial profile, retain replay/cancellation/epoch/financial metadata until an explicit retention/archival policy is qualified; no automatic pruning of unresolved exposure or tombstones is allowed. A handling policy must permit the necessary durable metadata before this recovery profile can admit its work; conflicting retention requirements make that work ineligible, rather than authorizing prohibited retention. No inferred inherited 397-day rule applies to these new records. Existing owner datasets keep their own policies. Default input persistence is off; result retention is bounded by current handling authorization, recommended maximum one hour for recoverable permitted results and zero for no-store work. Status/accounting survives result expiry and reports `result_available: false`; it does not replay to reconstruct output. These proposed defaults require D4 approval before activation.

Duranki restart reloads ledger, key/issuer/generation authority and cancellations before sends are enabled. A committed/possibly-sent call is never resubmitted; unknown cost retains the full hold. A definitive proven no-send transition may release a hold once. Duranki's own destructive restore is distinct from Ma'at restore: remain stopped and reconcile against retained independent send/financial evidence or preserve conservative exposure; a stale Duranki snapshot cannot safely reissue identities. Initial release claims preserving ordinary restart and tested backup/restore of the declared single-service state, not recovery from simultaneous loss of every independent ledger/evidence copy.

## 5. Generations, budgets, assembly and operator product

### 5.1 Model configurations and policies

A MODEL-CONFIGURATION generation is an immutable registered record: generation ID/revision, operation, exact model/revision/digest/family, destination and adapter/version, preparation/output-schema capability, parameter limits, embedding-space descriptor where applicable, rate/usage-contract versions and qualification evidence. `pinned` and `candidate` are named binding slots pointing to immutable generation IDs. Publication/rollback changes the slot for future authorization; it never changes a generation's meaning. An existing `execution_generation` remains an invocation identity and is not reused for this purpose.

Tokens request an exact generation. Candidate jobs require both an issuer-role candidate grant and a component-issued token naming that candidate; worker access alone cannot choose it. Ptah's agent still decides gold/shadow admission and prevents candidate results committing as live judgments. Model retirement returns `MODEL_UNSERVABLE`; no route substitution follows. Inference and embeddings obey current signed allowed destinations ∩ tenant/operator grants, family exclusions, operation capability and tools-off policy. Fail before provider bytes when no compatible route exists. Duranki does not walk Alexandria rests-on; the trusted component issuer computes that policy intersection from validated current source reads and signs it. Consumer two-worlds/commit tests remain essential.

Embedding generation metadata binds dimension, normalization, tokenizer/preprocessing recipe, document/query prefixes, immutable vector-space version and compatible index contract. A returned model or dimension mismatch is an explicit failed result with retained accounting. No truncation, reordering, silent field dropping or different-model fallback is permitted. Consumers own index builds, passage IDs and reindex/switch logic; Duranki is not a vector database.

### 5.2 Atomic caps and native accounting

Retain DEV-11's known/missing/null/explicit-zero distinctions and exact cache-aware arithmetic only for its reviewed rate domain. Retain successor native tariffs and linked revision-safe correction machinery. Generalize into shared internal hold/reservation logic rather than restoring a superseded two-rate eligibility path.

Register all claimed authoritative cap scopes (tenant, financial owner, and selected registered budget/engagement subscopes) before use. Signed engagement/budget labels provide linkage, not a balance or permission to create an unregistered spending account. A Ma'at budget ID may remain a consumer-owned ledger label while Duranki enforces its independently configured tenant/owner cap; it does not require manually registering every Ma'at reservation or engagement. If a profile additionally claims a Duranki per-budget/engagement cap, its matching authoritative scope must exist or the call refuses. Scope/ownership comes from service identity and current registry grants. Under the single-authority gate and one SQLite transaction, evaluate every applicable cap and reserve every hold together; budget failure rolls back **tentative holds only**, while the consumed/refused reservation, call and ledger decision persist durably. Implement one outer decision transaction and, if tentative writes are needed, a hold-only savepoint: reserve all applicable scopes on success; on budget denial remove tentative holds and commit one refused/no-attempt call plus reservation ownership and ledger row. Never roll back the refusal owner merely because capacity was denied.
