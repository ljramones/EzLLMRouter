## Implemented slice

The dedicated `duranki-dev06-local` Compose profile keeps the disposable test profile separate. It uses the real Coordinator and SQLite store, isolated LiteLLM worker, signed plan/final guard and trusted owned sender. The worker has no network and no trusted credential/code mount. The internal service/receiver namespace has no host binding. A fixed, credential-free ingress container from the pinned Python image publishes `127.0.0.1:8780` and forwards only to a dedicated Unix console socket. It has read-only root, no application credential or data volume, and joins only the dedicated publish network; it has no route to the receiver or sender socket. Service/worker run non-root with read-only roots; named volumes preserve permitted metadata across ordinary `down`/`up` without `-v`. Startup reclaims only a refused stale Unix socket and refuses an active or non-socket collision. The normal local entry has no test authority-control endpoint.

The console provides authenticated Overview, Activity/detail, Usage, Configuration and Build views over an allowlisted trusted-side projection of actual service state. It has an explicit **LIVE SYNTHETIC DEVELOPMENT** banner, bounded sessions, logout, Host/Origin and CSRF checks, no-store responses, read-only configuration, safe metadata fields, latest usage revision semantics and unknown cost. It never renders untrusted values as HTML. The fixed text, retained two-round caller-owned lookup and no-store text buttons use the installed Python SDK through the existing wire contract; the browser cannot set model URL, payload or signing authority. Launcher IDs persist before dispatch, repeated IDs return status, and interrupted launchers become `outcome_unknown` without automatic resubmission. These are launcher controls only.

The [operating README](../../../deploy/local/README.md) documents preparation, `up`, owned `restart`, `up-and-verify`, `status`, `stop`, the credential-file procedure and limits. `up-and-verify` is the single explicit target discriminator: it checks auth/readiness/topology, then intends exactly four new synthetic receiver requests and one caller lookup, checks service metadata/receipts, performs a quiescent stop/start and reads back permitted history. It leaves the profile running on success.

## Current local operation

The profile remains running at `http://127.0.0.1:8780/`. Stop without erasing metadata volumes:

```sh
python3 deploy/local/profile.py stop
```

The profile is intentionally left running after successful verification. On failure the script retains redacted logs in ignored `.state/commands/`, records a safe error, and stops only its own new profile containers. Historical Run-11 and Run-16 packets and failed-run records were not altered.

## Boundaries and next slice

This slice does not establish crash recovery, replay safety, complete no-store memory/WAL erasure, TLS/HTTP2, real-provider safety or whole-gateway qualification. The process signing key regenerates on normal startup; pending/unknown work is not resumed, and unavailable in-memory provenance is not reconstructed. Authenticated configuration lifecycle, approval/revocation and other real management operations are the next management slice. Secure-provider transport remains separately scoped.
