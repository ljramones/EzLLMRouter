## Exact selection and source inspection still required

When ordinary approved publisher HTTPS works, record the immutable GitHub release tag, resolve its commit through publisher records, obtain the official source archive as *inspection data*, check archive paths/types/links before extraction, and calculate its SHA-256. Record the publisher URL, retrieval time, response metadata and the distinction between a publisher checksum, a locally calculated digest, a verified signature/attestation and owner-accepted trust. Match the source archive to the release and to the intended PyPI **sdist** version; do not acquire a wheel or image under this authoring authority. Inspect the pinned license text, enterprise feature terms, release notes, security advisories and change history. A soak recommendation needs the actual release date and changes, plus the baseline's review and exception rule [architecture §4.4]. Neither an older familiar release nor the newest release is automatically cleared.

The pinned source inspection must trace the selected **non-streaming chat-completion route** in order: HTTP ingress/authenticated identity; request parsing and deployment lookup; message/tool/settings transformation; pre/during/post callbacks; selected provider adapter; retry and fallback decisions; final prepared HTTP request; and the actual transport send. Record each file, symbol and line at the resolved commit. The decisive question is whether a supported extension point can inspect the **final** prepared bytes and material transport controls *after all later mutations* and abort before every send. A pre-call callback or front-door admission alone does not establish that boundary. Check whether plugin registration is supported without a fork or installed-source edit. If final send is hidden, or a callback can mutate after the proposed check, B must report that limitation and inform DEC-09's thin-layer/alternative-gateway contingency; it may not call the boundary proven.

The source-path census must separately cover direct completion and Responses routes, streaming, provider passthrough (including the baseline's TypeSafe attribution concern), background/health traffic, proxy caching, automatic retries, router load balancing, fallbacks, alternate endpoints, logging/export and startup/runtime acquisition. Inspect both configuration enforcement and the code path that could bypass it. For any route excluded from initial `initial_1a@1`, prove startup rejection or request rejection; an untested route remains an obligation, not qualified coverage. The adopted initial surface permits text and supported tool calls, with fixed approved destination and no model substitution [contract §§3, 6, 8](../../contracts/wp-a-03-c01/DURANKI-WP-A-CONTRACT-v0.3-CORRECTION-01.md).
