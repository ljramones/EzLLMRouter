## Actors, destination and common evidence

Future project `duranki-wpb-<run-id>` has `driver` on `ingress`, guarded real `gateway` on `ingress` and `provider`, and independent `receiver` on `provider`. The synthetic model destination becomes **`http://receiver:8000/v1/chat/completions`**; the driver calls **`http://gateway:4000/v1/chat/completions`**. The synthetic adapter/route recipe must be regenerated and signed for these exact host/port/path controls, and its golden digest recalculated. An old loopback digest cannot be reused. The receiver alone records raw request bytes, headers, connection identity, sequence and response; gateway/intent, receiver and driver evidence use separate volumes.

For *every* negative B case, run a valid B-01 control before and after, identify the reached rejection stage, observe the receiver and namespace sockets through all gateway-task drain plus **five seconds**, and record the limit of that horizon. A dead receiver or shape rejection cannot count as FDC interception. Future supervisor captures exact argv, cwd, controlled environment, stdout, stderr, exit, artifact/config hashes, intent acknowledgments and receiver traffic. No case is executed by this kit.

## Required final-write and containment refinements

The `httpx.AsyncBaseTransport` guard is still a hypothesis. After final preparation it must compare independently derived expected body bytes and material method/URL/headers/timeout controls, then persist one intent and delegate once. It must freeze material data, carry correlation before final capture or through a defined separate channel, and recheck a revoked authorized-but-untransmitted attempt immediately before first write. A pool wait below the transport can defeat a transport-only recheck; exact lower-source inspection and dynamic proof are required. If a supported out-of-tree boundary cannot close this gap, B reports failure and DEC-09 returns to the owner.

Total attempt time includes pool wait, send and **complete response consumption** under one monotonic deadline, plus finite supervisor drain. Drip responses cannot extend the signed limit through repeated short reads. A cancelled queued task cannot later write. Each retry needs a signed next-attempt allowance, fresh FDC and fsynced intent. Shared-client interleaving of two differently signed principals/work must not cross contexts; missing/stale context rejects. An unguarded request to the *allowed* receiver is a mandatory bypass probe because network policy alone cannot detect it.

The future policy helper must default-deny gateway egress except frozen receiver IP:8000 and necessary DNS, permit driver ingress and established replies, and block gateway-to-driver, other loopback, host-management, public IPv4 and IPv6 routes. `internal: true`, labels and network memberships are insufficient alone. The helper's temporary `NET_ADMIN` and receipt are not implemented by this kit; the gateway wrapper must refuse to start untrusted code until policy verification passes. Neither Docker daemon access nor namespace policy was tested here.

After separate build and B1 issuance, the supervisor would use **only** `docker --context desktop-linux compose -p duranki-wpb-<run-id> -f tests/gateway-proof/docker/compose.yaml --env-file <approved-run-env> ...`, with exact project collision check, approved image digests and resource labels. The intended driver entry is `python -I -B /app/driver.py --case B-XX`; the authored Compose default command is `/app/driver.py` and the future driver must accept the supervisor's case argument. Policy setup, image build, `up`, `run`, receiver listeners and cleanup are **not authorized in DKR-01**. The future harness paths, key, recipe hashes and literal runtime argv must be frozen in B1 before use. The current files are specification and build preparation, not an executable proof.
