## 2. Contract and responsibility map

Draft a versioned network contract for ordered system/conversation/content blocks, tool schemas, explicit tool choice, tool-call/result IDs, source lineage and combined restrictions, resolved prompt/model inputs or controlled versioned references, request settings, cancellation, and capability negotiation. Responses need content blocks, structural status, actual served configuration, usage with raw and normalized categories and explicit unknown/estimated status, `attempt_id`, provider ID where present, error/retryability, and candidate-delivery status. Separate execution-status queries and outcome events distinguish transport completion from substantive step correctness and task acceptance. Source: baseline §§5.1–5.4, 8.1–8.5, 9–11; recce report §§3–5; readout §§3–4.

The trusted caller/orchestrator resolves prompts and models, labels every block and derived call, creates `step_id` + revision and `execution_generation`, owns tools and other effects, verifies substance, authorizes semantic recovery, and performs single-winner acceptance in its state store. The SDK transports and validates inputs for developer feedback; it cannot mint trusted identity, taint, authority, or acceptance. The server derives or validates authenticated principal and charging owner, performs admission, signs plans, prepares candidates with versioned adapters, and applies FDC after all callbacks. The gateway creates `attempt_id`, records intent before transmission, and keeps provider ID for reconciliation. The Phase 1a surface exposes identity levels without claiming Phase 1b deduplication, crash recovery, or compare-and-swap are already proven. Source: baseline §§5.1, 5.3–5.4, 8.2, 8.5; readout §§3.5, 5A.

Canonical-work binding covers principal, purpose, task/step/revision/generation and the assembled pre-adapter request. Candidate preparation binds each authorized deployment and adapter version; unversioned references are materialized or rejected. **Order:** prepare candidate → passing FDC → durably persist dispatch intent (**authorization point**) → transmit. FDC checks the final prepared request, current classification and permission, signature, versions, financial authorization and applicable lease on every enabled path. If persistence fails, do not transmit. If a revocation arrives after authorization but before transmission, re-check before transmission; a revocation after transmission is recorded and the attempt settles normally (baseline §5.4). Observed adapter changes, including cache-hint removal or forced-tool-choice weakening, are not approved behavior: preserve the semantic contract with a proven adapter or reject the combination. Phase 1a requests name an approved fixed destination, have no model substitution, and enforce spend limits and alerts without a hard concurrent ceiling (§§5.1, 5.3–5.5, 10.4). Supporting calls inherit policy and must be accounted for separately.

**P capability disposition:** include ordered text, structured tool/result exchange, explicit supported tool-choice subset, caller-side JSON salvage, materialized synthetic document text, service-principal/background and nested calls, and unknown usage. Propose explicit pre-dispatch rejection for streaming, realtime voice, audio/image generation, binary multimodal transport, direct Responses/web-search semantics, and uncontrolled provider-managed state until separately approved. A non-streaming synthetic analogue of a streamed source workflow is a new variant; it does not prove the source's streaming consumer. Capability exclusions are open decisions, not permanent baseline exclusions. The full Phase 1a test set still applies to enabled paths; first-relying-phase rules apply if a deferred capability is enabled earlier (baseline §16).

## 3. Evidence levels and phase roadmap

Evidence is labelled **specified**, **locally observed**, **standalone conformance**, **operational acceptance**, or **representative workload**. A synthetic cost ledger proves arithmetic and attribution under test inputs, not real cost per accepted task, task quality, traffic share, production latency, or savings. A local gateway experiment proves only the selected release and exercised paths; it is not the complete Phase 1a exit. Representative Phase 0 cohorts require later authorized observation of real tasks and acceptance; no Vega access is required to author this plan or develop the standalone harness. Sources: baseline §§1, 11, 15–16; readout §§2, 6.

## 5. Requirement and proof design

Evidence classes remain separate: component policy/adapter/ledger proof, cross-language canonical vectors, installed-package isolation, actual pinned gateway receiver proof, C1/C3 service conformance, D operational qualification, later fault/concurrency, and representative workload value. A client validator never proves server enforcement. Drive request → admission → signed plan → candidate preparation → **passing FDC → durable intent → transmit** → usage/candidate → orchestrator outcome. The independent receiver observes forbidden dispatch absence. A failed FDC, a failed intent persistence and a post-authorization revocation require distinct observations; an authorized but untransmitted attempt is re-checked after revocation (baseline §5.4). For T-09, mutate after binding with a controlled server adapter/callback; no test-only bypass enters production authority. Sources: baseline §§4.3, 5.4, 8, 10, 16; readout §5.

The register links every obligation to an implementation producer/milestone, acceptance owner, numbered tests where applicable and **unnumbered checks** where tests 1–41 do not cover the full requirement. A `complete` link means the stated intervention and observation cover that numbered test's canonical condition; `partial` or `relevance` never closes the test. Test records preserve canonical text and phase; their required interventions/observations identify what future proof must show. No application test has run. The overlay uses the same relationship labels, with proposed variants linked to their assertion groups. Test 17's enabled-stream lifecycle is not proven by initial unsupported-stream rejection.

Explicit non-numbered proof includes Nabu's approval-file loading/revocation/version checks; signed-plan decision records with deterministic propensity 1.0; three outcome levels and the Phase 2 full-instrumentation gate; avoidable incremental, allocated and full operating cost views and reports at their first use; later rules/cascades/recovery and predictor selection; baseline §6.5 admission + rules + local prediction ≤20 ms p99. Synthetic timing is a component diagnostic, not production p99 evidence. Enabled content stores, logs, caches and queues require retention/access controls as well as the telemetry allowlist (baseline §§5.5, 6.5, 9–10, 13). The register assigns owner, milestone and evidence for these. The orchestrator constructs leaf manifests; **Neti/gateway validates and rejects** invalid manifests (baseline §6.1, T-32).

The original 19-fixture catalogue remains unchanged. The overlay splits early unknown usage and spend checks from 1b exposure/recovery, identical generation from changed work/new generation, raw forgery from post-binding mutation, and initial streaming rejection from enabled behavior. It records where a fixture only relates to a numbered test. For `raw_no_financial_authorization`, ledger-rebuild exposure is a separate T-12 assertion. For `timeout_unknown_usage`, owner expiry and appended usage reconciliation have distinct T-10/T-18 assertions. Raw mutation has separate stale-policy and revocation interventions for T-07/T-08. `outline_and_draft` states the **currently authorized generation** and superseded result rejection. Server-interpreted canonical equivalence remains authoritative; a client hash never grants admission.

**Planning-data schema:** the register retains unique `WP-*`, `OB-*`, `T-01`–`T-41` IDs. Work packages carry start, produced, completion and operational gates plus milestone IDs; obligations carry producer/acceptance owner, source clauses, first functional milestone and evidence links. `coverage` is `complete`, `partial` or `relevance`. The overlay retains `original_fixture_id`, adds variant-to-assertion IDs and explicit test-coverage links, and records active profile, phase, owner, prerequisites and observation. These JSON files are planning data, not executable tests or adopted schemas.
